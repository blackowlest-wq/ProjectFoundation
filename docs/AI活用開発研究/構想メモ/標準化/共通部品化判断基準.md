# 共通部品化判断基準

## 目的

共通化の不足による重複と、過剰な共通化による複雑化の両方を防ぐ。
「似ているから共通化する」のではなく、同じ責務で同じ変更理由を持つかを基準に判断する。

## 共通化する

- 同じ責務で、変更理由も同じ処理が複数箇所にある。
- 認証、CSRF、API client、エラー応答、テストログイン補助など、誤ると影響が大きい処理。
- 仕様変更時に複数箇所を同時修正する必要が高い処理。
- 呼び出し側に不要な実装詳細が漏れている処理。
- テストやE2Eで同じ準備処理を繰り返している処理。

## 共通化しない

- 見た目や処理手順が似ているだけで、業務意味や変更理由が違う。
- 仕様がまだ揺れていて、抽象化すると変更しにくくなる。
- 1箇所だけの処理で、再利用見込みが低い。
- 共通化により引数や分岐が増え、呼び出し側より共通部品の方が複雑になる。
- 業務機能ごとの言葉や状態を、無理に汎用名へ変換する必要がある。

## 保留する

- 将来増える見込みはあるが、現時点で利用箇所が少ない。
- 既存実装との差分が大きく、別作業として安全に進めた方がよい。
- 共通化の責務境界に迷う場合。
- 共通化後の回帰確認コストが高く、今回の作業範囲を超える場合。

保留する場合は、保留理由、再確認タイミング、候補となる配置先を作業記録に残す。

## 優先的に共通化を検討する処理

| 領域 | 例 |
| --- | --- |
| フロントAPI | `fetch`、CSRFヘッダー、`credentials: 'include'`、エラー変換 |
| 認証 | ログイン状態確認、ログアウト、認証エラー処理 |
| バックエンドテスト | MockMvcログイン、CSRF付与、テストユーザー作成 |
| E2E | 認証モック、静的配信、共通操作、APIモック |
| エラー処理 | エラーコード、HTTPステータス、画面表示メッセージ |
| DB/マスタ | マスタ取得、状態判定、共通クエリ |

## 共通化後の確認

- 利用元の代表テストが通るか。
- 型チェック、ビルド、静的解析が通るか。
- 共通部品の名前が責務を表しているか。
- 共通部品が特定機能に依存しすぎていないか。
- 呼び出し側のコードが以前より読みやすくなっているか。

## カスタムLinterの責務集中に関する判断（2026-09-12）

今回の判定は「標準化候補」かつ「保留」とする。Frontendの旧regex代替経路は削除し、公開ESLint Node API（`lintFiles` / `lintText`）とRuleTesterの入口を同値性の証跡として扱う。一方、`frontend/eslint-rules/index.mjs`のrule registryと、backendの`EndpointMetadataRegistry.java`の検出・比較責務は、現行機能の変更理由がまだ一つであり、今すぐ分割するとseamと回帰範囲を増やすため今回の実装範囲では分割しない。

次回、policy追加、owner追加、または別の接続方式を追加する機能変更が入った時点で再評価する。その際は、catalog読込、rule登録、診断整形、実Spring handler mappingの列挙、metadata比較の変更理由を分離して利用箇所・テスト責務を確認し、分割する場合も公開入口を変えずに内部moduleを分ける。分割後は公開入口／internal seam同値性、A/B/D/Cの代表ケース、既存のFull gateを再実行してから共通部品化を完了扱いにする。

### 最終レビュー追加判定（2026-09-12）

- module edge検出のAST visitors（import、type-only、named/all re-export、static dynamic import、qualified/global member、単純alias）は、現状は同じFrontend Aの依存・transport境界という変更理由を持つため、今回さらに分割しない。shared→auth、auth→appの完全edgeとshadowing、`apiClient`例外は同一の公開lint契約で維持する。
- 非リテラルdynamic importと再代入aliasを静的判定対象外とするのは、現行の構文解析責務とflow解析コストの境界である。flow解析または新しい迂回ポリシーを追加する時は、rule registry、解析器、diagnostic、公開adapterの変更理由が分かれるかを再評価し、専用caseとFull gateを先に固定する。
- TC-PFL-085のevidence validator、Stage marker chain、Impact expected completeness、backend runtime metadata fail-closedは、各々content gate、orchestration、aggregate、observabilityの異なる責務である。共通化は検証データ形式の共有に留め、変更理由が独立した時だけ内部moduleを分割する。
- FIND-LUNA-P1-005（schema v2と文書の双方向整合）とP1-006（全105 locatorのsymbol/selector実在検証）は、content gateの証跡validatorという同じ変更理由に属するため、別部品へ分割せず同一契約で維持する。v2のpath、symbol、case、public command、hash、status、exit検証を共有し、schemaやlocator言語を拡張する時だけvalidator分割要否を再評価する。
- FIND-LUNA-P1-007（sourceArtifact pinの自己参照循環）は、P1-005/006と同じcontent gateの証跡責務として扱う。pinの値を各docsへ複製せず、`scripts/fixtures/project-lint/TC-PFL-085-post-review-gate/post-review.json::executionEvidence.sha256` をcanonical locatorとして参照する。文書更新後の再固定・双方向整合・具体hash複製禁止を同一契約で維持し、schemaまたはartifact構成を変更する時だけvalidator分割要否を再評価する。
