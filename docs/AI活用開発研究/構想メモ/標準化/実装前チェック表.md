# 実装前チェック表

## 目的

AIに実装を依頼する前に、仕様・既存実装・テスト方針・記録方針を揃える。この資料は、作業ごとに結果を埋めるチェック表と、実装前のチーム共通判断基準を兼ねる。

## 使い方

- 実装前のPlanフェーズで確認する。
- この資料は、作業ごとに確認結果を埋めるチェック表として使う。
- 不明点は「確認事項」として分離する。
- 軽微な仮定で進める場合は、仮定と理由を作業記録へ残す。
- チェック結果を埋めるだけでなく、今回の対象範囲、適用するP0/P1/P2観点、対象外・保留理由を記録する。
- 長期保守性は、絶対条件、全変更の必須核、変更リスクに応じた適用観点の3層で適用する。3層は既存のP0/P1/P2レビュー優先度を置き換えず、適用対象と証拠を決めるために使う。
- 全変更の必須核として、変更影響、変更結果の検証、重要な判断・前提の追跡方法を決める。重要な設計判断は既存ADRを参照するか、新規ADRを作成する。
- テストを追加・変更する場合は、実装前にテスト構成・責務対応表を作り、既存テストの分割・維持判断とテスト層を確定する。全テスト成功はこの確認の代わりにしない。
- 機能単位の統合品質記録を正本として特定し、レビュー詳細資料へ同じ実行結果やCI URLを重複転記しない。
- レビューはBackend/DB/Security、Frontend/UI、Integration/Finalの3チェックポイントへ集約する。P0/P1/P2の観点、独立判定、統合担当は維持する。
- 作業開始時に簡易修正モードまたは品質重視モードを選択し、選択結果を1枚の変更記録へ残す。品質重視モードでは本表と既存Hard Gateを適用する。

## 簡易修正モードの実装前確認

簡易修正モードを選択した個別変更では、専用仕様書、実装計画、AC/TC/RT台帳、実装後レビュー文書を新規作成しない。代わりに1枚の変更記録へ、次を記録する。

- 受入条件3～5項目
- Focused Unit対象、またはN/A理由
- 表示要件の有無。表示要件がある場合は既存Playwrightの1ケース、または手動確認理由
- 変更対象層のlint / typecheck / build結果
- コード差分の独立レビュー1回
- 全テスト、coverage、全E2E、Oracle、追加secret scanをCIへ委譲したこと
- 既存hookと`main` push後の6品質jobを維持すること

Simpleでも、API契約、DB、DDL、SQL、業務ルール、状態遷移、入力検証、CI、workflow、品質ゲートを対象から除外しない。該当する場合はFocused Unitや対象層チェックの入力へ反映し、未実行項目は理由とCI確認先を記録する。

## 適用する確認観点の優先度

| 優先度 | 適用内容 |
| --- | --- |
| P0 | 対象範囲、設計・受入条件、正本ケース、期待結果、トレーサビリティ、テスト構成・責務境界、外部ドキュメント、TDD/BDD、最終ゲートを確認する。 |
| P1 | 認証・認可・CSRF・入力検証、配置・共通化、静的解析・CI、ログ・観測可能性を変更内容に応じて確認する。ログは本資料の「ログ設計」と`セキュリティ規約.md`を主資料とする。 |
| P2 | 性能、競合、互換性、アクセシビリティ、移行・復旧などを明示要件または変更リスクがある場合に確認する。 |

P1/P2を適用しない場合も、理由または保留条件を作業記録へ残す。
