# テストケースレビュー観点

## 目的

単体テスト、API/Controllerテスト、フロント単体テスト、E2E、Oracle/DB接続テストをレビューするときに、仕様担保、境界値、実装分岐、品質補完の抜け漏れを確認するための共通チェックリストを定義する。

## 使い方

1. 対象機能の受入条件、入力チェック、業務ルール、非機能要件を確認する。
2. 既存テストケースを下記チェックリストに対応付ける。
3. 判定は `OK`、`不足`、`対象外`、`保留` のいずれかにする。
4. 受入条件ID、過去障害・指摘ID、テストケースID、実テストIDの対応を確認する。
5. 期待結果が仕様根拠、観測可能性、十分なアサーションを持つかを独立に確認する。
6. `不足` は追加候補として記録し、仕様上必要か、カバレッジ目的か、回帰防止目的かを分類する。

自動レポートの検出結果と人手レビューの判定は分離する。自動検出は必須項目、ID、紐付け、実行状態、品質ゲート、カバレッジなど機械的に照合できる事実に限定し、AIが意味解釈した「不足」「要補足」を自動確認項目へ混在させない。

## 基本観点

| 観点 | 確認内容 |
| --- | --- |
| ブラックボックス | 仕様書、API一覧、受入条件どおりの入力と出力を確認しているか |
| ホワイトボックス | 実装上の重要な分岐、例外、状態変化を確認しているか |
| 正常系 | 代表的な成功パターンを確認しているか |
| 異常系 | 不正入力、未認証、権限不足、存在しないデータを確認しているか |
| 最小値 | 入力可能な最小値、最小件数を確認しているか |
| 最大値 | 許容最大値、最大文字数、上限件数を確認しているか |
| 境界値 | 境界値そのものと境界の外側を確認しているか |
| 同値分割 | 同じ扱いになる入力群から代表値を選んでいるか |
| 区分値・Enum網羅 | 定義済み区分を全件確認しているか。未定義値を拒否しているか |
| 組み合わせ | ロール、状態、区分、入力有無などの組み合わせを確認しているか |
| デシジョンテーブル | 条件が多い業務ルールを表にして漏れなく確認しているか |
| 状態遷移 | 正常遷移、不正遷移、遷移後の副作用を確認しているか |
| 状態別画面操作 | 状態ごとに入力、明細追加・更新・削除、保存、提出の許可/拒否を一覧化しているか |
| 読込中・読込失敗 | 詳細取得中・取得失敗時に初期値の誤保存や状態不明の操作が発生しないことを確認しているか |
| null・未指定 | null、未指定、空配列などを確認しているか |
| 空文字・空白 | 空文字、半角空白、全角空白を確認しているか |
| 形式チェック | 日付、時刻、年月、コード形式などを確認しているか |
| 桁数・精度 | 文字数、数値桁、丸め、分単位などを確認しているか |
| 重複・一意制約 | 同じキーや業務上一意のデータを拒否できるか |
| 存在チェック | 参照先データや対象データが存在しない場合を確認しているか |
| 権限・所有者 | 自分、他人、上長、管理者など権限差を確認しているか |
| 順序・並び替え | 一覧や検索結果の順序を確認しているか |
| 件数 | 0件、1件、複数件、大量件数を確認しているか |
| 複数データ読み込み | 複数レコードや複数ロールの読み込みで期待どおりか |
| N+1 | データ件数増加時にSQLや処理回数が不自然に増えないか |
| 排他・同時実行 | 同時更新、古い状態、二重実行を確認しているか |
| 副作用 | DB更新、セッション、ログ、イベントなどの副作用を確認しているか |
| 冪等性 | 同じ操作を複数回実行しても破綻しないか |
| タイムゾーン・日付境界 | 月末、年末、日跨ぎ、タイムゾーン差異を確認しているか |
| マスタ属性駆動 | 画面とBackendがマスタ属性を同じ業務ルールの根拠として使い、未知の区分・空マスタ・取得失敗で固定値を保存しないか |
| DB seed同期 | ソース既定値、DataInitializer、手動seed SQL、API/fixtureのキー・本文・有効フラグが一致し、未登録・無効行・seed漏れを確認しているか |
| 保存中・通信順序 | 保存中の二重送信、先行した詳細取得による状態の巻き戻り、保存後の再取得失敗を確認しているか |
| Backend計算結果表示 | Backendで確定した計算値を登録・更新後に画面で確認でき、未保存の古い値を表示し続けないか |
| ロケール・文字種 | 日本語、全角、記号、改行、絵文字などを確認しているか |
| セキュリティ | 認証、認可、CSRF、XSS、SQLインジェクションを考慮しているか |
| エラー処理 | 期待するステータス、エラーコード、メッセージ、詳細を返すか |
| DB依存 | 実DB、方言、制約、型差異を確認しているか |
| 回帰テスト | 過去の不具合やレビュー指摘の再発を防ぐテストがあるか |
| カバレッジ補完 | 未通過分岐を意図して確認しているか。仕様担保との違いを明記しているか |

## テスト構成・責務分割観点

テストが成功することと、テスト構成が保守可能で漏れを検出しやすいことは別に判定する。実装前と実装後、Full実行前に次を確認する。

| 観点 | 確認内容 |
| --- | --- |
| 責務境界 | テストファイルが機能、ユースケース、コンポーネントの境界に沿い、認証・一覧・登録・編集など独立した責務を不必要に混在させていないか |
| テスト層境界 | Unit/UI/API/E2E/Oracleの目的と実行環境が一つのファイルへ不必要に混在していないか |
| ファイル集中 | 一つのテストファイルに複数責務のdescribe、fixture、モックが集中し、変更時の影響範囲やレビュー単位を不明確にしていないか |
| 分割・維持判断 | 分割する場合は対象ファイル、責務、移動範囲、維持する期待値を明示し、分割しない場合は理由と再確認条件を記録しているか |
| 移動の同値性 | 分割・移動でテスト名、アサーション、fixture、モック応答、ケースID、実テストIDが意図せず変わっていないか |
| 共通support | 複数ファイルで共有する準備・fixture・操作helperがsupportへ整理され、特定の代表テストだけに隠れていないか |
| トレーサビリティ | テスト構成・責務対応表から正本ケース、実テストファイル、テスト名、実行コマンドを追跡できるか |
| Fullとの区別 | Full成功を構成レビューの証拠とせず、構成レビューの判定とFull結果を別々に記録しているか |

## 区分値・Enumがある場合の重点観点

| 観点 | 確認内容 |
| --- | --- |
| 定義済み値の全件確認 | Enumや区分値を全件1回以上確認しているか |
| 未定義値の拒否 | 存在しない区分値、空、nullを拒否しているか |
| 区分ごとの業務差分 | 区分によって結果や権限が変わる箇所を確認しているか |
| 区分と状態の組み合わせ | 区分 × 状態 × 操作の許可/拒否を確認しているか |
| 追加時の変更容易性 | Enum追加時にテストが不足を検知できるか |

## トレーサビリティ観点

| 観点 | 確認内容 |
| --- | --- |
| 受入条件との紐づけ | 各テストケースに受入条件IDがあり、未対応の受入条件が対象外・保留を含めて明示されているか |
| ID名前空間 | 受入条件、テストケース、実テスト、指摘のIDを別名前空間で管理し、同じ文字列を再利用していないか |
| 過去障害との紐づけ | 過去障害・レビュー指摘に関連する回帰テストがあり、欠陥IDとテストケースIDが相互参照できるか |
| 実テストとの紐づけ | テストケースからテストメソッド、spec、実行結果、証跡を追跡できるか |
| 孤立ケース | 要求・障害・探索目的のいずれにも紐づかないケースがないか |
| 重複・矛盾 | 同じ目的の重複ケースや、期待結果が矛盾するケースがないか |

## 期待結果レビュー観点

| 観点 | 確認内容 |
| --- | --- |
| 仕様根拠 | 期待結果が受入条件、設計、過去障害のいずれかに根拠づけられているか |
| 観測可能性 | API本文、画面、DB、セッション、イベント、ファイルなど確認対象が具体的か |
| 検出力 | 仕様違反や条件反転が発生した場合にテストが失敗するアサーションか |
| 副作用 | DB更新、状態変更、ログ、通知、セッションなど必要な副作用を確認しているか |
| テスト層適合 | 単体、API、画面、E2E、Oracleの適切な層で確認しているか |
| UIスタイル観測 | レイアウト・色・余白を受入条件に含むUIでは、DOMクラス確認だけで完了扱いにせず、computed style等のブラウザ観測または正本CSS契約を確認しているか。jsdomでCSSが適用されない場合はE2E・目視を別証跡にしているか |
| 曖昧さ | 仕様不明点を推測で期待結果にせず、確認事項・保留としているか |

## 過去障害・回帰観点

| 観点 | 確認内容 |
| --- | --- |
| 未検出理由 | 既存テストで検出できなかった理由が、ケース不足、期待結果不足、データ不足などに分類されているか |
| 回帰テスト | 修正後に同じ障害を検出できるテストが追加・修正されているか |
| 横展開 | 同じ原因が他機能にも存在しないか確認しているか |
| 標準化反映 | 受入条件、ケース様式、レビュー観点、プロンプト、サンプルの必要な箇所へ反映されているか |

## カスタムLinter実装後の追加標準化観点（2026-09-12）

カスタム静的解析を追加する場合は、内部実装の成功ではなく、利用者が呼ぶ公開入口の契約を正本にする。公開entry（A/B/C/D）と内部seam（Node API、validator、Spring mapping）の入力、diagnostic schema、終了コード、stdout/stderrが同値であることを確認し、internal helperの直接呼出しやregexによる別経路を成功証拠にしない。

- 意図的REDは、期待signatureを実際に不一致にした子processが非0（assertion mismatchはexit 1）になることを確認する。テスト名・フラグ・自己申告だけでREDを成立扱いにしない。
- content gateは、`postReviewStatus=complete`などの自己申告を信頼せず、必要artifact、AC/TC/RT/FINDのID範囲、ケース一件一行、stale marker、実行結果を実ファイルから再検査する。未実行・skip・artifact不足は`OK`にしない。
- wrapperを追加する場合は、既存規約を保存するbase lintを必ず通し、custom rulesだけの成功を許さない。Quick/PrePushはbase-only（custom rules off）とし、設定変更時はbaseの全体`eslint .`を実行する。custom policyの接続はcatalog-derived contractで確認する。
- 入力ファイルは対象拡張子・text rootを明示し、strict UTF-8 decode errorを診断してbinaryを誤検出しない。invalid UTF-8は実行不能（exit 2）であり、黙ってskipしない。
- catalogやfixtureの値はuntrustedである。diagnosticのpolicy identity・messageへ値を無制限に補間せず、秘密canaryがstdout/stderrのどちらにも出ないことを確認する。missing propertyは親objectの固定anchorなど、再現可能な位置契約を使う。
- schemaVersionのような数値契約はfraction、bool、stringを個別に拒否し、指数表記を許容する場合はparse後の数学的同値性と、その理由を記録する。可変catalogでも、接続登録のない第7 policyは受け入れない。
- baselineは「歴史時点の検出証跡」と「修正後回帰」を別ケースにする。固定点とのblob確認だけではA/D実行証跡を代替しない。artifact未取得は`保留`とし、次回変更でStage順序・不変保存条件を再実行する。
- Dのroute検証は手書きController一覧を正本にせず、実Spring `RequestMappingHandlerMapping`とcentral registryを比較する。framework/non-API除外、methodless拒否、multi-method展開などの境界は一原因ずつ実証する。

### 責務集中の分割判断

カスタムruleのindex/registryが複数policy、診断変換、公開adapter、catalog接続を同時に担う場合は、現時点の利用元・変更理由・テスト境界を棚卸しする。今回のregex代替は削除して機能責務を維持したが、`frontend/eslint-rules/index.mjs`やEndpoint metadata registryの責務分割は、次回policyまたはownerを追加する機能変更時に再評価する。再評価では、catalog/diagnostic、rule registry、公開adapter、orchestrationの変更理由が独立しているか、分割後の利用元代表テストと契約テストを確保できるかを判定し、未確定のまま過剰分割しない。

## 最終レビュー追加標準化観点（2026-09-12）

### 証跡・ゲートの実在性

- content gateのTCは、completion flagや文書上のPASSだけで完了にしない。証跡のrepository-relative pathが実在し、locatorのsymbol名とcase IDがsourceへ存在し、public runnerがそのpath/caseを実行していることを突合する。
- execution evidenceはschema v2を正本とし、19 source artifacts、105明示coverage、104 PASS＋TC-PFL-074限定HOLDを検証する。各executionのpublic command、exitCode、result、stdout/stderr hashと、source hash/artifact pin、commitを相互突合する。現行pinは `scripts/fixtures/project-lint/TC-PFL-085-post-review-gate/post-review.json::executionEvidence.sha256` を唯一正本とし、sourceArtifact対象docsはlocatorだけを参照して具体hashを複製しない。旧schema v1、default/all-HOLD、未許可HOLD、coverage欠落/重複、reason/recheck欠落はnegativeで失敗させ、PASSはexit 0だけ、HOLDは許可された未実行だけを表す。文書更新後はpinを再固定して最終状態を同期する。
- 全105ケースのlocatorは`path::symbol/selector`を必須とし、PowerShell関数、Java method、TS/JS test selectorの実在とcase一致を検証する。path-only、空symbol、架空symbolをTC-PFL-085相当のnegativeで拒否し、pathの存在だけを実テスト証跡とみなさない。
- Impact aggregateはselected layerをすべてexpected集合へ含める。Quality/Oracleごとの許可除外以外のmissing layerやmissing mapは失敗とし、集合・除外の変更時はTC-PFL-121相当を追加する。
- Stage 1〜5はStage 0 markerだけで進めず、各Stageが直前までの完了markerを連鎖して要求する。前提欠落の全順序をTC-PFL-120相当のnegativeで確認する。
- backendのlive metadataはSpring lifecycleで実mappingとregistryを突合し、不一致を非開示例外でfail-closedにする。不一致起動失敗と整合起動成功の両方をTC-PFL-130/131相当で確認する。
- sourceArtifact pinが自己をhash対象に含む可変証跡である場合、本文へ具体値を複製せずcanonical locatorだけを記録する。docs更新後のpin再固定前に生じるhash mismatch/HOLDは一時状態として扱い、最終レビューの判定へ持ち越さない。TC-PFL-074の歴史baseline HOLDはこのpin運用とは別契約である。

### AST・依存境界・迂回

- suppressionは文字列検索でなくparserのAST `SourceCode` comment tokenを使い、line/block commentだけを対象にする。文字列・template内の`eslint-disable`は診断しない。直前の`Why not:`とrule IDの正負を分けて確認する。
- module依存edgeは通常importだけでなくtype-only import、named/export-all re-export、static dynamic importを含め、shared→auth、auth→appを欠落させない。type-only許可は例外として明示する。
- transport禁止は`window`/`globalThis`/`self`のqualified/global fetch・cookieと単純const aliasを検出し、shadowingと`apiClient`例外を保持する。非リテラルdynamic importと再代入aliasは現行の静的判定対象外であること、flow解析を追加する機能変更時の再確認条件を記録する。
- 上記110〜121/130〜131はレビュー回帰subcaseであり、canonical TC-PFL-001〜105の件数へ混在させない。既存ケースの責務を変える場合は、同じ原因・同じ観測へ統合できるかを先に確認する。
