# ProjectFoundation 品質確認レポート作成

## 原則

対象機能をユーザー指定の機能ID・機能名で限定し、既存の表示データテンプレート、機能別フォルダ、生成スクリプト、一括検証を再利用して静的HTMLを作成する。新しい形式や機能固有の事実を推測して作らない。

判定の代わりに、入力された正本資料と機械的に検証できる事実を表示する。`合格`、`評価A`、`総合判定`、`承認可能／承認不可`をAIの意味解釈で生成しない。未実行、失敗、保留、未通過分岐、品質ゲートの状態などは事実として分離して表示する。

対象機能が依頼に含まれない場合は、機能IDまたは機能名を確認してから作業する。別機能のデータを流用して補完しない。

## 作業手順

1. **対象と既存状態を確定する**

   - `docs/AI活用開発研究/コード品質確認画面/<機能フォルダ>/` を探す。
   - `品質確認表示データ.template.json`、対象機能の`*_表示データ.json`、`*_生成.ps1`、`*_表示方針.tests.ps1`、`README.md`を確認する。
   - 受入条件、テストケース正本、品質レビュー、実テスト、証跡、ソース、カバレッジ、品質ゲート運用を確認する。正本の対応は [quality-report-commands.md](references/quality-report-commands.md) を参照する。
   - `git status --short` と `git diff --check` を確認し、既存の未コミット変更を保護する。既存HTMLを再生成する場合は、上書き対象と変更理由を記録する。

2. **表示データを用意する**

   - 対象機能の表示データがない場合は、共通テンプレートを対象機能フォルダへコピーする。`F-001`の事実・ID・証跡を別機能へコピーしない。
   - `schemaVersion` は `1.0` とする。`feature`、受入条件、品質ゲート、テストケース、観点、実テスト、証跡、指摘、カバレッジ、ソースを正本資料の内容で埋める。
   - IDはコレクション内および全体で一意にし、受入条件→ケース→実テスト→証跡の参照を実在IDへ揃える。期待結果・実行結果・基準値は資料に記載された値だけを転記する。
   - 入力JSONに`automatedFindings`を追加しない。これは生成物であり、スクリプトが必須項目、ID、参照、実行結果、品質ゲート、カバレッジ、明示された保留を検証して作成する。
   - `reviewStatus`、`caseDesignStatus`、指摘の`要補足`などの人手レビュー記録は保持するが、AIが意味を解釈して機械検証結果へ変換しない。

3. **既存形式で検証・生成する**

   対象機能を明示して、まず検証だけを実行する。

   ```powershell
   pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-quality-reports.ps1 `
     -FeaturePath .\docs\AI活用開発研究\コード品質確認画面\<機能フォルダ> `
     -ValidateOnly
   ```

   検証が成功した場合だけ、同じ対象を指定してHTMLを生成する。

   ```powershell
   pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-quality-reports.ps1 `
     -FeaturePath .\docs\AI活用開発研究\コード品質確認画面\<機能フォルダ>
   ```

   一括更新を依頼された場合だけ`-FeaturePath`を省略する。新機能の生成スクリプトがない場合は、既存の機能パターンを構造だけ再利用し、対象機能の正本データを確定してから作る。

4. **結果を確認する**

   - 共通契約テスト、機能固有回帰テスト、`-ValidateOnly`、HTML生成の終了コードを確認する。
   - レポートは`NG・要確認`タブなど、問題・未実行・保留・未通過を確認できる表示を使う。OK件数を表示すること自体は許容するが、そこから総合評価を推論しない。
   - `file://`のブラウザ表示を自動確認できない場合は、HTMLの構造検証までと明記し、目視確認済みとは報告しない。ブラウザ確認が必要ならユーザーに再読み込み・目視確認を依頼する。
   - Backend、Frontend、Oracle、Full、E2E、カバレッジ再生成などを実行していない場合は、未実行の事実、理由、再確認条件を残す。未実行を成功として扱わない。

5. **記録して引き渡す**

   `docs/AI活用開発研究/作業記録/コード品質確認画面_検証記録.md`へ、対象機能、変更ファイル、参照した正本資料、実行コマンド、終了結果、表示した事実、未実行事項と再確認条件を記録する。

   レビュー指摘を新たに検出した場合は、作業記録だけで終わらせず`docs/AI活用開発研究/作業記録/日報登録編集_指摘一覧.md`にも追加し、`個別対応`、`既存観点で対応`、`標準化候補`、`対象外`、`保留`のいずれかと根拠を記録する。

## クイックチェック

| 確認 | 合格条件 |
| --- | --- |
| 対象 | ユーザー指定の機能フォルダだけを更新している |
| 正本 | 受入条件、ケース、実テスト、証跡、ソースの出典が追跡できる |
| 入力 | `schemaVersion=1.0`、必須項目、ID、参照、基準値が揃っている |
| 自動判定 | 入力に`automatedFindings`がなく、意味評価を生成していない |
| 検証 | 共通契約、機能固有テスト、ValidateOnly、生成が成功している |
| 表示 | 問題・未実行・保留・未通過が事実として分かる |
| 記録 | 変更、未実行、制約、再確認条件が作業記録にある |

## よくある誤り

- 対象機能を確認せず、最初に見つかったF-001のデータを新機能へコピーする。
- JSONに前回生成した`automatedFindings`を戻し、入力と生成物を混在させる。
- `要補足`、レビュー保留、テスト未実行をAIの解釈で`不足`や`不合格`へ変換する。
- `-ValidateOnly`を省略して直接HTMLを生成する。
- HTMLが生成できたことだけを根拠に、テスト実行済み、カバレッジ最新、ブラウザ目視済みと報告する。
