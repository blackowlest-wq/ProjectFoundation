# テスト方針

## 目的

チーム作業でテスト範囲と品質ゲートの判断を揃え、未確認のまま実装を進めることを防ぐ。

## 基本方針

- 業務ルール、入力検証、状態遷移、認証認可は自動テストを優先する。
- 画面操作の主要フローはE2Eで確認する。
- Mock E2Eは画面の操作・表示・分岐を安定して確認し、実Backend/Oracle E2EはログインからDB永続化・再読込までの接続実効性を確認する。両者は代替ではなく補完関係とする。
- 実Backend/Oracle E2Eでは、Backendログ、Frontendログ、Playwrightレポート、Oracle検証結果を取得し、相関ID・HTTP結果・業務状態変更を追跡できるようにする。認証情報を含み得るOracle E2EのPlaywright trace/video/screenshotは無効化し、Backendログを主な障害追跡記録とする。
- Oracle固有のDDL、SQL、制約、接続設定に関わる変更はOracle実機確認を検討する。
- 通常実行では、変更機能、直接依存先、関連契約テスト、必要なE2E / Oracleを影響範囲から選択する。夜間・リリース前は、全テスト、全coverage、全E2E、必要なOracleを全体実行する。
- 全体実行や全体coverageの成功だけで、変更機能のテスト十分性、分岐未充足の確認、テスト構成レビューを代替しない。
- テスト未実行の場合は、未実行理由と再確認条件を作業記録に残す。
- テストコードはWhat（何を検証し、何を期待するか）をテスト名、`describe`/`it`、Arrange/Act/Assertの構造で示す。実装手順の逐語説明は避けるが、テストデータの意図や複雑な前提がないとWhatを誤読する場合はコメントを残す。
- レイアウト・色・余白などCSSの適用結果が受入条件に含まれる画面変更は、フロント単体のDOM契約に加えて、E2Eまたはブラウザ目視でcomputed styleを確認する。jsdomでCSSを適用できない場合は、単体テストの成功だけで表示確認を完了扱いにしない。
- Oracle接続情報は `backend/config/oracle-test.properties` で管理し、バックエンドテストは共通のOracle入口を使用する。具体的な実行方法は [品質ゲート運用.md](品質ゲート運用.md) と `scripts/check.ps1` を参照する。

## テスト分類

| 分類 | 主な対象 | 目的 |
| --- | --- | --- |
| バックエンド単体/結合寄り | Controller、Service、Repository | 認証、入力検証、業務ルール、DB更新を確認する |
| フロント単体 | API client、validation、UI部品 | 画面ロジックと表示分岐を確認する |
| E2E | ログイン、日報登録、編集、提出など | ユーザー操作として主要フローが通ることを確認する |
| Mock E2E | APIを制御したFrontend操作 | UIの表示、入力、状態遷移を安定して確認する |
| Backend/Oracle E2E | 実Backend、実Oracle、実Frontend | 接続、認証、CSRF、DB保存、再読込、ログ相関を確認する |
| Oracle実機確認 | DDL、SQL、マスタ、制約 | 開発用DBとOracle差異による不具合を検出する |
| 静的解析 | TypeScript、Java、依存関係、secret | 型不整合、危険な実装、機密情報混入を検出する |

## テスト配置とユースケース分割

- フロント単体テストは `frontend/test` に配置する。
- フロントE2Eのspecとhelperは `frontend/e2e`、`frontend/e2e/support` に配置する。
- バックエンドの単体テスト・結合寄りテスト・`*IT.java` は `backend/src/test` に配置する。
- テストクラスは、本番のController / Service と同じユースケース境界に合わせ、検索/詳細、登録/更新、提出/再提出、マスタAPIなどの責務で分ける。
- 共通のログイン準備、fixture、seed投入は test support に置き、代表テストから必ず利用される形にする。
- テストファイルも本番コードと同じ責務境界で分ける。認証、一覧、登録・編集など独立したユースケースや、Unit/UI/E2E/Oracleなど異なるテスト層を一つのテストファイルへ集中させない。
- 既存テストを変更する場合は、実装前に「テスト構成・責務対応表」を作り、テストファイル、責務、テスト層、対象本番モジュール、ケースID/実テストID、分割・維持判定、理由を記録する。
- 分割時は期待値、アサーション、fixture、モック応答、テストケースIDを維持し、共有fixture・UI操作・通信モックだけを共通supportへ移す。維持する場合は、責務が混在しない理由または分割しない制約を記録する。
- Fullテストの成功、カバレッジ、配置チェックはテスト構成レビューの代替ではない。構成・責務レビューを先に完了し、その後にFullを最終ゲートとして実行する。
- `scripts/check-test-layout.ps1` は配置構造の品質ゲートであり、単体、結合寄り、E2E、typecheck、build、Oracle確認を置き換えるものではない。
- 影響範囲ベースで通常実行対象を選択した場合は、テスト構成・責務対応表または同等の変更記録へ、選択したテスト、除外したテストや層、その理由、全体実行へのフォールバック有無を残す。

## 影響範囲ベースの実行選択

通常実行では、変更ファイル名だけで完了扱いにせず、変更機能、直接依存先、関連契約、必要な表示確認、必要なOracle確認までを対象に含める。

| 変更種別 | 通常実行で選択する対象 | 全体実行へのフォールバック条件 |
| --- | --- | --- |
| 画面の局所変更 | 対象画面や部品のフロント単体、関連Mock E2E / E2E、表示要件がある場合のcomputed style確認、直接利用元の代表テスト | 利用元が広く特定できない、画面共通レイアウトへ波及する、表示崩れが複数画面へ及ぶ |
| APIの局所変更 | 対象Controller / Service / Repositoryテスト、関連するフロントAPI client / validation、関連Mock E2E / E2E | 複数APIで共有する例外変換、共通レスポンス整形、外部I/F契約の波及範囲を限定できない |
| 共通部品・共有fixture・test support | 利用元の代表Unit / API / E2E、関連契約テスト、fixture利用テスト | 利用元が広範囲で代表ケースに絞れない、fixture変更が複数機能の前提を変える、共通部品が責務過多で影響境界を切れない |
| 認証・認可・CSRF | 対象Controllerテスト、認証guardやtoken処理のフロント単体、ログインを含む主要Mock E2E、必要なBackend/Oracle E2E | セッション、権限、CSRF token、共通filterが複数機能へ横断影響する、認証失敗系の波及範囲を限定できない |
| 業務ルール・状態遷移 | 対象Service / Controller / Repositoryテスト、条件分岐を持つフロント単体、主要ユースケースのE2E、必要なOracle確認 | ルールが共通計算や承認経路など複数ユースケースへ波及する、状態遷移の組合せが広く影響範囲を限定できない |
| DB / SQL / DDL / マスタ | 対象Repository、`*IT`、必要なService / Controller、関連Oracle実機確認、必要なBackend/Oracle E2E | migration、共有SQL、共通マスタ、索引・制約変更が複数機能へ波及する、Oracle差異を局所確認だけで説明できない |
| workflow・test runner・テスト発見規約・集約build・依存関係・coverage設定 | 変更した層の契約テスト、coverage gate contract、関連lint / build / test。通常判定でも該当層は全体実行前提で扱う | 実行対象の選択ロジック自体が変わるため、影響範囲選択を信用できない。該当層の全体テスト、全coverage、必要なE2Eへ拡張する |
| 影響範囲不明・密結合・高リスク | 選択可能な代表テストを先に実行しつつ、通常判定は全体実行へフォールバックする | 依存関係を判定できない、分離不能な共通依存がある、障害影響が大きい、変更理由や除外理由を記録できない |

- 影響範囲の選択では、選択した対象だけでなく、除外したテスト層と除外理由も記録する。
- `workflow`、テスト基盤、依存関係、coverage設定の変更は、テスト選択器そのものの信頼性へ影響するため、局所成功だけで完了扱いにしない。
- 密結合や影響範囲不明を理由に全体実行へフォールバックした場合は、その変更記録へ長期改善候補も残す。候補には責務分割、依存グラフ整備、fixture分離、契約テスト追加を含める。

## カバレッジの二層基準

| 層 | 実行タイミング | 必須確認 | 禁止事項 |
| --- | --- | --- | --- |
| 変更単位coverage | 開発中、通常CI、通常の`main` push後 | 変更行、変更モジュール、影響範囲のStatements / Branches / Functions / Lines、およびBackendのINSTRUCTION / BRANCH / METHOD / LINEを確認し、分岐未充足をblockingで扱う | 全体coverageの数値だけで、変更機能のFocused Unit、契約テスト、主要E2E、必要なOracle確認を省略しない |
| 全体coverage | 夜間、リリース前 | Frontend / Backendのcoverage artifactを全体実行で再生成し、全体退行、artifact不足、threshold未達、未実行を失敗として扱う | 全体coverageの成功だけで、変更機能の十分性やテスト構成レビューを完了扱いにしない |

- 変更単位coverageでは、変更行と変更モジュールの双方を確認し、影響先の分岐が未充足のまま残らないようにする。
- 変更範囲を抽出できない場合、または共有設定変更により対象範囲の信頼性が崩れる場合は、coverage確認も全体実行へフォールバックする。
- 夜間・リリース前の全体coverageは通常実行の不足を補完するための再生成であり、通常実行で選んだ変更機能の妥当性確認を置き換えない。

## 品質ゲート

- 通常テストが成功している。バックエンドテストは共通のOracle入口から実行し、共通化されたOracle接続設定を読み込む。具体的な実行方法は [品質ゲート運用.md](品質ゲート運用.md) と `scripts/check.ps1` を参照する。
- TypeScript型チェックとフロントビルドが成功している。
- 変更対象の主要E2Eが成功している。
- 静的解析を導入済みの場合、重大以上の指摘が残っていない。
- 通常実行では、変更行、変更モジュール、影響範囲のcoverageと分岐未充足を確認し、変更対象の十分性を記録する。
- 夜間・リリース前は、Frontend / Backendの全体coverage artifactを再生成し、artifact不足、threshold未達、未実行を成功扱いにしない。
- 全体coverageの成功、Fullの成功、配置チェックの成功だけで、変更機能のFocused Unit、契約テスト、主要E2E、必要なOracle確認を省略しない。
- Frontend / Backendのcoverageレポート確認は必須とし、Statements / Branches / Functions / Lines、およびINSTRUCTION / BRANCH / METHOD / LINEの4指標をそれぞれ85%以上に保つ。
- Frontendは`frontend/coverage/coverage-summary.json`、Backendは`backend/target/site/jacoco/jacoco.xml`を入力として、`scripts/write-coverage-summary.ps1`で各指標と85%ゲート判定をCI job summaryへ出力する。HTML、XML、CSVのレポート存在確認と既存のthreshold engineがblocking判定の責任を持ち、summary出力だけで成功扱いにしない。
- Oracle不要のBackend単体テストは`main` push後のGitHub-hosted runnerで実行し、Oracle接続なしで業務ルール・共通例外・観測性・repository計算の回帰を検出する。
- Branches / BRANCHは分岐未充足を直接示すblocking指標として扱い、85%未満なら品質ゲート未通過とする。
- uncovered behaviorが見つかった場合は、その条件を再現するテストを追加し、同じcoverage入口を再実行して結果を更新する。
- 未実行の確認がある場合は、理由と再実行条件を作業記録に残す。

## テストコードのWhat確認

- Javaの`@Test`メソッド名から、対象操作、条件、期待結果が読める。
- Vitest/Playwrightの`describe`、`it`、`test`から、検証対象と期待結果が読める。
- テスト名で確認内容を表現できる場合、実装手順を説明するコメントを追加しない。
- テスト名を変更する場合も、期待値、アサーション、fixture、モック応答は変更しない。

## テスト追加の判断

| 変更内容 | 優先するテスト |
| --- | --- |
| 入力チェック変更 | バックエンドテスト、フロント単体テスト |
| 業務ルール変更 | Serviceテスト、Controllerテスト |
| 画面操作変更 | フロント単体テスト、E2E |
| 認証認可変更 | Controllerテスト、E2E |
| DB/SQL変更 | Repositoryテスト、Oracle実機確認 |
| 共通部品変更 | 利用元の代表テスト、回帰テスト |
