# 長期保守可能性を重視した品質方針

## 目的

本プロジェクトは、SIer向けのシステム開発・保守を支援する開発環境を検討する。

SIer向けシステムでは、数年単位の保守、担当者や協力会社の交代、業務知識が十分でない担当者による調査、古いシステムの改修、障害時の短時間の影響判断が発生する。また、仕様書と実装が一致していない場合もある。

このような環境では、現在の開発者だけが理解できる状態では不十分である。将来の保守担当者が、根拠を追跡しながら安全に理解し、変更し、検証し、障害時に調査・復旧できることを、品質の中心に置く。

## 主な読者

第一の読者は、将来の保守担当者、協力会社、引継ぎ担当者とする。

現在の開発者、AI利用者、レビュー担当者は、後任者が必要な情報を追跡できる状態を作るための副次的な読者とする。

## 長期保守可能性の定義

長期保守可能性とは、システムを十分に知らない担当者であっても、必要な情報を追跡しながら、安全に理解し、変更し、検証し、障害時に調査・復旧できる性質である。

保守容易性は、コードの読みやすさだけを意味しない。次の品質を含む上位概念として扱う。

- システムや処理の構造を理解できる
- 変更影響を把握できる
- 変更結果を検証できる
- 障害の原因を調査し、復旧につなげられる
- 担当者が交代しても知識を引き継げる

## 品質の絶対条件と優先順位

以下は、保守性や開発速度との比較対象ではなく、満たすことを前提とする。

- 正しく安全に動作すること
- セキュリティ要件を満たすこと
- 法令・契約要件を満たすこと

絶対条件を満たした上で、長期保守に関する優先順位を次のとおりとする。

1. 変更影響を把握できること
2. 変更結果を検証できること
3. 未経験者でも構造を理解できること
4. 障害時に原因を調査し、必要な復旧につなげられること
5. 実装やリリースが速いこと

これは速度を否定する方針ではない。ただし、速度だけを理由に、影響範囲、検証方法、構造、障害調査に必要な情報を失わせない。

## 長期保守可能性を支える品質領域

保守性はコード品質だけでなく、設計、テスト、運用、ドキュメント、AI利用時の判断記録を含む品質である。

| 品質領域 | 保守担当者が確認できるべきこと |
| --- | --- |
| 設計 | システムの構造、責務、境界、前提、重要な設計判断 |
| 実装 | 処理の責務、契約、制約、変更してよい範囲、影響を受ける範囲 |
| テスト | 何を保証しているか、変更時に何を再確認すべきか、異常系や境界値の扱い |
| 運用 | ログや相関IDから何が起きたかを調査できること、復旧判断に必要な情報があること |
| ドキュメント | 全体像、処理・データフロー、外部境界、実行方法、重要ルール、設計理由 |
| AI利用 | AIの提案と人間の最終判断を区別できること、採用・修正・不採用の理由を追跡できること |

## ドキュメントは量ではなく、保守価値と更新可能性で判断する

保守性向上のためにドキュメントを増やすことは自然だが、ドキュメントは多いほどよいわけではない。

AIは大量の説明資料を容易に作成できる。しかし、更新されない資料や、コードをそのまま日本語化しただけの説明は、実装との不一致を増やし、後任者を誤った判断へ導く可能性がある。

残す価値が高い情報は、次の3群を中心とする。

- **全体像・境界**: システム全体の構成、処理・データフロー、外部システムとの境界
- **実行・調査**: ローカル実行方法、テスト実行方法、障害調査方法
- **判断・制約**: 重要な設計判断、変更してはいけない制約、業務上の重要ルール

コード、テスト、設定、CIなどの実行可能な情報を一次的な根拠とし、文書はそれらから読み取りにくい理由、全体像、境界、制約、運用上の判断を補う。

文書を追加するときは、少なくとも次を考える。

- 誰のどの判断に役立つか
- 何が変わったときに更新するか
- 実装や実行可能な情報との不一致をどう防ぐか

仕様書と実装が一致しない場合も、理想仕様だけで現状を説明しない。確認できた現行挙動、仕様上の前提、確認できていない事項を区別し、後任者が誤解しないようにする。

## AI利用時は、対話履歴ではなく判断結果を残す

AIとの会話をすべて保存することを目的にしない。対話には途中案や誤った提案も含まれ、そのままでは後任者にとって信頼できる設計資料にならないためである。

AIとの対話から人間が確認し、採用した最終的な判断として、少なくとも次の情報を追跡できるようにする。

- 何を実現する変更だったか
- どの設計・実装案を採用したか
- なぜその方式を採用したか
- どの代替案を検討し、なぜ採用しなかったか
- どの仕様、制約、業務ルールを前提にしたか
- どのリスクを認識しているか
- AIが生成した内容のうち、どこを人間が確認、修正、採用したか
- どのテストやレビューで安全性を確認したか

AIの出力は提案または下書きとして扱い、採用の根拠と最終判断は、人間が後から追跡できる形で残す。AIとの対話そのものを正本とはしない。

## 保守担当者から見た確認視点

長期保守可能性を実務へ結びつけるため、保守担当者が次の問いに答えられる状態を目指す。

1. この機能・処理は何を実現し、何を保証するものか
2. どのファイル、データ、外部システム、業務ルールに関係するか
3. なぜ現在の構造・方式になっているか
4. 変更後の安全性を、どのテスト、レビュー、確認で判断できるか
5. 障害時に、どこから調査し、どの状態を確認し、どう復旧につなげるか

これらに答えられない場合は、コードだけでなく、設計、テスト、ログ、運用情報、ドキュメントのどこかに保守上の不足がある可能性がある。

## 既存の標準化資料との関係

この文書は、長期保守を前提に、何を品質とみなすかを示す上位方針である。具体的な確認手順、記録様式、テスト方針、レビュー観点は、既存の標準化資料を正本とする。

重要な設計判断は、[ADRテンプレート](../設計判断記録/ADRテンプレート.md)を使ったADRを正本とする。作業記録は作業の経過、統合品質記録はテスト・レビュー・品質ゲートの実行結果を担い、ADRの判断内容を重複転記しない。AIとの対話全文や生成コードの行単位の採用範囲は保存せず、設計判断は背景、決定、代替案、前提・制約、関連資料へ集約する。

- [品質向上施策メモ](./品質向上施策メモ.md): AI活用による品質向上の研究方針
- [ADRテンプレート](../設計判断記録/ADRテンプレート.md): 重要な設計判断を記録する最小様式
- [開発フロー](./標準化/開発フロー.md): 方針をIntakeからRecordまでの開発手順へ落とし込む
- [実装前チェック表](./標準化/実装前チェック表.md): 実装前の確認項目と判断基準
- [実装後レビュー表](./標準化/実装後レビュー表.md): 実装後のレビューとAI生成物確認
- [テスト方針](./標準化/テスト方針.md): テスト範囲、テスト層、責務分割の判断基準
- [テストケースレビュー観点](./標準化/テストケースレビュー観点.md): テストケースとテスト構成のレビュー観点
- [統合品質記録様式](./標準化/統合品質記録様式.md): 受入条件、テスト、指摘、レビュー、品質ゲートの統合記録
- [作業記録テンプレート](./標準化/作業記録テンプレート.md): 作業・レビュー・指摘の記録項目

## まとめ

長期保守における品質とは、現在の担当者がシステムを動かせることだけではない。将来の担当者が、根拠を追跡しながら、安全に理解し、変更し、検証し、障害時に調査・復旧できることである。
