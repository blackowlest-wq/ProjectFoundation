## 2. 承認する仕様具体化

Do開始の承認には、次の設計判断への承認を含む。

- 社員別は`daily_reports.work_minutes`、案件別・分類別は`daily_report_work_items.work_minutes`を正とする。
- 休日区分別日数は、承認済み日報の休日区分別社員日数（`COUNT(*)`）とする。
- `work_minutes=null`の承認済み休日は社員別0分として残す。
- API 0件は4空配列、UIは対象社員0名・総作業0分・4空状態とする。
- 初期年月はブラウザのローカル年月とする。
- 4集計切替はWAI-ARIA tabsの自動選択方式とする。
- 正常時の概要は対象社員数と総作業時間だけとし、根拠が未確定の有給日数・休日作業カードは作らない。
- API配列の並び順は契約化しない。

## 3. 外部一次情報

- Spring JDBC Core: <https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html>
- Java 21 `YearMonth`: <https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/YearMonth.html>
- React `useEffect`: <https://react.dev/reference/react/useEffect>
- W3C WAI-ARIA APG Tabs Pattern: <https://www.w3.org/WAI/ARIA/apg/patterns/tabs/>

判断への反映:

- SQL値はbind parameterで渡し、Repositoryは固定個数の集合集約を返す。
- `YearMonth`の解析前に`^[0-9]{4}-[0-9]{2}$`へ完全一致させ、契約外の拡張年・空白・日付を拒否する。仕様にない年範囲は追加しない。
- Reactの非同期取得はcleanup/世代番号で旧応答を失効させる。
- tabsは`tablist/tab/tabpanel`、関連ARIA属性、左右矢印、自動選択を実装する。

## 4. 実装seamと責務

TDDで先に固定する公開seamは次の4点である。承認後、内部実装ではなくこの観測面をREDにする。

1. Backend: `GET /api/monthly-summaries`と`MonthlySummaryService`。認可・入力・4集計・エラー・ログを観測する。
2. Frontend: `getMonthlySummary(yearMonth)`、`MonthlySummaryPage`、Appのロール/401接続。HTTP要求とDOMを観測する。
3. Mock E2E: ログイン後のルート、年月変更、4tabs、空状態、非管理者のAPI未要求を観測する。
4. Oracle E2E: 日報登録→提出→承認→月次表示、監査列、4集計、相関ID、cleanupを観測する。

### 4.1 Backend

- `backend/src/main/java/com/example/dailyreport/monthlysummary/`へController、Service、Repository、DTOを置く。
- Serviceは認可を最初に行い、EMPLOYEE/MANAGERでは年月解析やRepository呼出しの前に403とする。
- 年月は正規表現完全一致後に`YearMonth.parse`し、`atDay(1)`以上`plusMonths(1).atDay(1)`未満の半開区間へ変換する。
- 対象月は`report_date`で判定し、`approved_at`では判定しない。
- Repositoryは全Entityを取得せず、社員・案件・分類・休日の最大4本の集約SQLを固定回数で実行する。各SQLで期間と`APPROVED`を絞る。
- 社員SQLは`COALESCE(SUM(dr.work_minutes), 0)`、休日SQLは`COUNT(*)`を返す。案件/分類は承認済み日報へjoinする。
- `@Transactional(readOnly = true)`、bind parameter、既存`ix_daily_reports_calendar`と`ix_daily_report_items_report`を利用する。DDLは追加しない。
- 共通`ApiExceptionHandler`と`ErrorResponse`を再利用し、個人名・年月query・SQL・内部例外をエラーやログへ出さない。
- `RequestMetadataInterceptor`に加え、Securityより前に動く`RequestContext.featureForPath`と`USE_CASE_ROUTES`へ月次pathを登録し、401でも`MONTHLY_SUMMARY`を記録する。

### 4.2 Frontend

- `frontend/src/monthlySummary/`へ`types.ts`、`monthlySummaryApi.ts`、`MonthlySummaryPage.tsx`、`monthlySummary.css`を置く。
- APIは既存`getJson`を使い、Cookie、共通エラー、401契約を維持する。
- Pageは入力中年月と表示中年月を分け、「集計表示」で取得する。初期値だけローカル年月を生成する。
- 最新要求の世代番号またはAbortControllerで旧応答を失効し、遅い過去月で現在表示を上書きしない。
- 取得開始時に旧エラーを消し、失敗時は旧概要/4表を消す。401は`onUnauthorized`を1回通知し、Appが利用者状態とURLを破棄する。
- 概要は社員配列件数と社員別分の合計。時間表記の変換はせずAPI契約どおり分を表示する。
- Appはロール/パス判定と`onUnauthorized`接続だけを持ち、ADMINログイン後に`/monthly-summaries`へ遷移する。日報画面との同時描画をしない。
- 月次fixtureは`dailyReportTestSupport.tsx`へ混ぜず、月次専用supportへ置く。4表はF-011配下の局所部品とし、shared汎用表を先行作成しない。

### 4.3 Oracle E2E

- 既存`oracle-daily-report.oracle.spec.ts`の2099-12-01 PENDING契約は維持する。
- 新規`monthly-summary.oracle.spec.ts`は2099-12-02、E001、WORKDAY、09:00～18:00、P001/WC001=480分を登録・提出・承認する。
- `test-e2e-oracle.ps1`はspecごとのreport IDを曖昧な最初のCREATEログではなく、識別可能なmarkerまたは固定日+社員でverifyへ渡す。
- `e2e-verify.sql`は12-01 PENDINGと12-02 APPROVED、480分明細、承認者・承認日時を検証する。
- `e2e-cleanup.sql`は両固定日を実行前後に日報明細→日報の順で削除し、再実行可能にする。
- requestIdはcreate/submit/approve/summaryを回収し、Backend完了ログとPlaywright/Oracle成果物を追跡する。
