# F-001 ログイン機能 コード品質確認画面設計

## 背景

テストケース、実テスト、ソースコード、カバレッジ、レビュー記録が機能ごとに分散しており、ログイン機能の品質確認時に、受入条件から実行証跡までを一続きで確認しにくい。

本設計では、`F-001 ログイン`をパイロット対象として、既存資料を正本として参照しながら、テストケースの棚卸し、トレーサビリティ、不足抽出、実行証跡を静的HTMLで閲覧できるようにする。

## 目的

- 受入条件、テストケース、実テスト、証跡の対応関係を機能単位で確認できるようにする。
- テストケースレビュー観点を一覧化し、確認漏れを明示する。
- 未対応の受入条件、孤立ケース、期待結果不足、未実行、未通過分岐を抽出する。
- 生成したHTMLをローカルでダブルクリックして閲覧できるようにする。
- 将来、他機能へ同じ形式を展開できるファイル構成を確立する。

## 対象範囲

### 実装対象

- `F-001` ログイン機能の品質確認画面
- `S-001` ログイン画面
- `/api/auth/login`
- `/api/auth/logout`
- `/api/auth/me`
- ロール別初期画面遷移
- Cookieセッション、CSRF、セッションID再発行
- Backend、Frontend、Oracleのテストケースと実テスト対応
- 実行結果、レビュー結果、カバレッジ結果、未確認理由の表示

### 対象外

- ログイン機能そのものの実装変更
- 既存テストケースやソースコードの仕様変更
- カバレッジ閾値や品質ゲート運用の変更
- Oracle接続情報、パスワード、トークン、個人の認証情報の表示
- すべてのMarkdownを自動解析する汎用ドキュメント変換基盤
- ブラウザからテストを実行する機能

## 表示用データモデル

表示用JSONは次の概念を持つ。

| 項目 | 目的 |
| --- | --- |
| `feature` | 機能ID、機能名、画面ID、対象範囲、スナップショット情報 |
| `acceptanceCriteria` | 受入条件ID、内容、判定、対応ケースID |
| `testCases` | テストケースID、テスト層、目的、前提、操作、期待結果、受入条件ID、実テストID、証跡ID |
| `viewpoints` | 観点ID、観点名、確認内容、判定、根拠ケースID、未確認理由 |
| `testImplementations` | 実テストID、ファイル、テスト名、実行コマンド、実行結果 |
| `evidence` | 証跡ID、種別、相対パス、取得日時、対象コミット、備考 |
| `findings` | 指摘ID、分類、対象ID、内容、優先度、対応状況、標準化判定 |
| `coverage` | Frontend/Backend別のレポート状態、指標、未通過分岐、未生成理由 |
| `sources` | 正本資料、参照節、相対リンク |

ケースID、受入条件ID、実テストID、指摘IDは既存の名前空間を維持する。表示画面固有の抽出結果には、必要に応じて`CQ-F001-*`の名前空間を使用する。

## 判定モデル

異なる意味の判定を一つのステータスへ集約しない。

### レビュー判定

`OK`、`不足`、`対象外`、`保留`

### 実行結果

`成功`、`失敗`、`未実行`

### カバレッジ判定

`通過`、`未通過`、`未生成`、`対象外`

カバレッジレポートが存在しない場合は、未通過分岐として扱わず、`未生成`または`未確認`として表示する。これにより、証拠がないことと分岐を通過していないことを混同しない。

## 画面構成

### 概要

画面上部に次を表示する。

- 受入条件数
- テストケース数
- 実テスト数
- 観点数と不足数
- 期待結果不足数
- 未実行・保留数
- Frontend/Backendカバレッジ状態

### トレーサビリティ

次の階層を相互に追跡できるようにする。

```text
受入条件
  └─ テストケース
      └─ 実テスト
          └─ 実行結果・証跡
              └─ ソース・カバレッジ
```

受入条件に未対応ケースがある場合、ケースに実テストがない場合、実行証跡がない場合を別々に表示する。

### 観点一覧

ProjectFoundationの`テストケースレビュー観点.md`とログイン固有のセキュリティ観点を、次のような単位で表示する。

- 正常系、異常系
- 最小値、最大値、境界値、同値分割
- 必須、空文字、空白、形式、桁数
- ロール、認証、認可、CSRF、セッション
- 状態遷移、副作用、冪等性
- API、画面、DB、Oracle
- 期待結果の仕様根拠、観測可能性、検出力
- 回帰、過去障害、トレーサビリティ
- テスト構成、責務分割、テスト層境界

### 不足抽出

次の項目を警告として抽出する。

- 受入条件に紐づかないテストケース
- テストケースに紐づかない実テスト
- 実テストに具体的なアサーションがないケース
- 期待結果の仕様根拠または観測対象が不明なケース
- 未実行、保留、失敗のケース
- カバレッジ未通過分岐
- カバレッジ未生成・未確認
- 過去障害・レビュー指摘に対応する回帰テストがないケース

「不足」と「対象外・保留」は別表示にし、対象外・保留には理由と再確認条件を表示する。

### 証跡・ソース参照

既存のMarkdown、テストコード、ソースコード、カバレッジHTML、レビュー記録へ相対リンクする。画面内へソースコード全文やログ全文を複製せず、参照元へ遷移できるようにする。

## 生成方式

- `F-001_ログイン_生成.ps1`が表示用JSONを読み込む。
- 生成スクリプトはJSON、CSS、JavaScript、HTMLを一つのHTMLへ埋め込む。
- 生成後のHTMLは外部サーバー、npmパッケージ、CDNを必要としない。
- `README.md`へ生成コマンド、参照元、リンク切れ確認方法を記録する。
- HTML生成時に対象コミットと生成日時を画面へ埋め込む。

初回は既存資料からログイン機能の表示用データを明示的に作成する。Markdown全体の自動解析は対象外とし、同じ構造を他機能へ展開する際に自動抽出の必要性を再評価する。

## セキュリティ・情報管理

- パスワード、Oracle接続情報、トークン、Cookie値、秘密値は表示用データへ含めない。
- テストユーザー名やIDを表示する場合も、実環境の資格情報と混同しないようにする。
- ログやスクリーンショットを複製せず、機密情報を含まない既存証跡だけへリンクする。
- HTMLを公開場所へ配置する前提は置かず、リポジトリ内の開発資料として扱う。

| CQ-F001-AC-005 | カバレッジ未通過分岐とカバレッジ未生成を区別できる | カバレッジ表示と未生成状態を確認する |

## テスト方針

- JSONの必須項目、ID重複、参照先IDの存在を生成スクリプトの検証で確認する。
- HTML生成後、主要見出し、件数、判定、警告、リンク先が出力されていることを確認する。
- `file://`でHTMLを開き、外部リソースなしで表示できることを確認する。
- PowerShellスクリプトの構文チェックと、生成結果の再生成確認を行う。
- Markdown lint、secret scan、既存の品質ゲートを実行する。
- 既存のアプリケーションテストの成功は、品質確認画面の表示・リンク・抽出ロジックの検証とは分けて記録する。

## 仮定

- 既存のログイン機能資料に記録されたケースID、実テストID、レビュー判定を初回スナップショットへ反映する。
- 現時点でBackendカバレッジ成果物がない場合は、未生成・未確認として表示する。
- 既存証跡の相対パスはリポジトリルートから解決できる構成を前提とする。

## 保留事項

- Markdownから受入条件・テストケースを自動抽出する汎用化は、F-002以降で再評価する。
- Backendカバレッジの実行結果は、Oracle接続環境と対象コミットが揃った時点で更新する。
- HTML上でのソースコード埋め込みや高度なグラフ表示は、初回パイロットの評価後に必要性を判断する。
