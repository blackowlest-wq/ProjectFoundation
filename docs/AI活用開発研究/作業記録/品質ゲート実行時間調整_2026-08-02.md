# 品質ゲート実行時間調整 作業記録

## 目的

テスト実行時に3分上限へ到達してから再実行する運用を減らすため、CIのQuality workflowとローカル実行の初期timeout基準を見直す。

## 調査結果

- リポジトリ内にローカル実行ツールの3分上限を指定する設定はなかった。
- GitHub Actionsの`jobs.<job_id>.timeout-minutes`はjob単位の実行上限で、未指定時の既定値は360分である。参照: [GitHub Actions workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)。
- Oracle workflowの`oracle-integration`、`oracle-coverage`、`oracle-e2e`は既に30分設定だった。
- Security workflowのDependency Auditも30分設定だった。

## 対応内容

- `.github/workflows/quality.yml`の8 jobへ`timeout-minutes: 10`を追加した。
- `scripts/impact-workflow.tests.ps1`へQuality workflow全jobの10分設定を検証する契約を追加した。
- `品質ゲート運用.md`へローカル初期値を追記した。
- Oracle/Securityの30分設定は変更していない。

## 検証

- 修正前の`pwsh -NoProfile -File scripts/impact-workflow.tests.ps1`: RED。`impact-plan`の10分設定不足を検出。
- 修正後の同契約テスト: GREEN。
- Oracleの30分契約は既存の`coverage-gate.tests.ps1`で再確認する。
- Markdown lint、`FullBackend`、pre-pushで最終確認する。

## 標準化判定

`標準化候補`。Quality workflowのjob上限とローカル実行の初期timeoutは、個別テストではなく全品質ゲートで再利用する実行基準であるため、品質ゲート運用資料とworkflow契約テストへ反映した。
