# 品質ゲート外側timeoutガード 2026-08-05

## 開発モード

- 品質重視モード
- 対象: `scripts/check.ps1`を起動するローカル・CI補助実行の外側timeout案内
- 対象外: GitHub Actionsのjob timeout値、テスト内容、テストの並列化、Oracle接続設定

## 目的

2026-08-05の`Full`実行で、呼び出し側の120秒上限がテスト完了前に到達した。これはテスト失敗ではなく、外側の実行ツールがプロセスを終了させた事象である。実行対象ごとの十分なtimeoutを実行入口から提示し、短い上限で開始してから再実行する手戻りを防止する。

## 根因調査

- `scripts/check.ps1 -Mode Full`を外側timeout 120秒で起動したところ、終了コード124で呼び出し側が終了した。
- その後、同じcommitを外側timeout 600秒で再実行すると、初回キャッシュ・コンパイル済み環境で258.1秒で成功した。
- `main`へマージ後の再コンパイルを含む`Full`も、外側timeout 600秒で330.5秒で成功した。
- `.github/workflows/quality.yml`のQuality各jobは10分、`.github/workflows/oracle.yml`のOracle各jobとSecurityのDependency Auditは30分で、既存契約テストも設定値を検証している。
- したがって、今回の直接原因はリポジトリのCI上限不足ではなく、ローカル呼び出し側の120秒設定である。

## 対応内容

- `scripts/check.ps1`へ`Get-QualityTimeoutBudgetSeconds`を追加し、Quick/PrePush 180秒、Full系600秒、Oracle/coverage/E2EOracle/All/Dependency Audit 1800秒を返すようにした。
- `scripts/check.ps1`の起動時に、呼び出し側へ設定すべき推奨timeoutを秒・分で表示するようにした。
- `scripts/quality-timeout.tests.ps1`を追加し、Mode、CiTask、ImpactTaskごとのtimeout対応を契約化した。Fullの契約テスト群から自動実行する。
- `品質ゲート運用.md`へ、120秒などの短い外側timeoutを使用しないこと、timeout終了時はテスト失敗と判定せず十分なtimeoutで再実行することを追記した。
- GitHub Actionsの10分／30分設定は現状で実測値を満たしているため変更しない。

## レビュー計画・判定

- P0: 品質ゲート運用資料と実行入口の整合、契約テストの期待結果を確認する。
- P1: `check.ps1`の品質ゲート・CI契約変更として、workflow timeout値を変更しないこと、既存job契約が維持されることを確認する。
- P2: 実行時間の増加傾向は今回の固定値変更の対象外。Fullの実測値を作業記録に残し、600秒を超える兆候が出た場合に再評価する。
- 標準化判定: **標準化候補**。外側timeoutの設定誤りは全品質ゲートで再発し得るため、実行入口の案内、品質ゲート運用資料、契約テストの3点で維持する。

## 残る確認事項

- 実行ツール自体のtimeout値はリポジトリから強制変更できないため、PowerShell、IDE、エージェントの呼び出し側で推奨値以上を設定する運用が必要である。
- 600秒を超えるFull実行が継続する場合は、job timeoutを含む品質ゲート運用の再評価を行う。
