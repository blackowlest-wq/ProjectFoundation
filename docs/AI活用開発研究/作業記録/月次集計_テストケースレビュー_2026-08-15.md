# 月次集計 テストケースレビュー

## 1. レビュー情報

- 対象機能: `F-011 月次集計`、`A-016 GET /api/monthly-summaries`、`S-008 月次集計画面`
- レビュー日: 2026-08-15
- 対象資料: `月次集計_テストケース.md`、受入条件、実装後レビュー、テスト方針、テストケースレビュー観点
- 対象実装・テスト: BackendのController/Service/Repository/observability、FrontendのPage/App/API、Mock E2E、Oracle E2E、Oracle runner
- レビュー方式: 正本ケースの入力・期待結果・要件・RT、実テストのアサーション、テストファイルの責務、実行記録を突合
- 判定: `OK`=観点を満たす、`不足`=ケースまたは実テストに不足、`保留`=仕様・環境・実行証跡待ち、`対象外`=F-011の対象範囲外

## 2. 総合判定

**ケース正本は「主要機能を記述できている」が、テストケースレビュー完了とは判定しない。**

正常系、`APPROVED`限定、4集計、空配列、認証・認可、年月形式、UIのtabs/競合など、受入条件に対応するケースは揃っている。しかし、次のP0/P1相当の不足がある。

1. DBの状態除外・複数行GROUP BY・同日複数社員・境界・read-only・ログを、正本どおりのfixtureで実行できる証跡がない。
2. 定義済み休日区分5種のうち、ケースは`WORKDAY`、`HOLIDAY`、`PAID_LEAVE`の3種しか扱わず、`AM_OFF`、`PM_OFF`を集計ケースで確認していない。
3. Mock E2E/Oracle E2Eの案件・分類・休日表は行集合の完全一致と非対象行不存在を一貫して確認していない。Unitの完全一致だけでは上位層の契約を証明できない。
4. Oracle verifyが別specで作る`2099-12-01`のPENDING行に依存するが、`TC-F011-ORACLE-001`自身は`2099-12-02`しかfixtureとして宣言していない。
5. `再集計を継続可能`、`再試行可能`と記載しているが、空状態からの再集計、400後の再試行を実際に操作していない。

したがって、通常のFrontend/Backend Unit・Mock E2Eゲートは部分的に良好だが、DB/Oracleを含むF-011のケース完了判定は保留する。既存の`FIND-F011-POST-BE-001`、`FIND-F011-POST-GATE-001`、`FIND-F011-POST-SEC-001`、`FIND-F011-FM-001`、`FIND-F011-FM-002`は本レビューでも有効である。

## 4. 指摘事項

### FIND-F011-TC-REV-001: 休日区分の列挙網羅不足（P1）

- 対象: `月次集計_テストケース.md` §4、`TC-F011-BE-004`、DB概念設計の休日区分コード、`seed-master-data.sql`
- 問題: 定義済み`WORKDAY`、`HOLIDAY`、`PAID_LEAVE`、`AM_OFF`、`PM_OFF`のうち、集計ケースで確認するのは前3種だけである。`未知・余分な区分はない`は、DBのFK制約があるため集計APIの観測可能な期待結果になっていない。
- 影響: 半日休暇が休日区分別集計から欠落しても、現在のケースは検出しない。未知値を確認したい場合はDB不正値ではなく、マスタ制約または入力境界の別ケースに分ける必要がある。
- 判定: `不足`
- 標準化判定: **標準化候補**。列挙値×承認状態×null/明細有無のマトリクスを、集計機能の共通ケース観点へ追加する。
- 対応案: `AM_OFF`/`PM_OFF`を含む具体的な日付・社員・期待日数をBE-004へ追加し、未知値の主張は削除するかDB制約ケースへ分離する。

### FIND-F011-TC-REV-002: fixtureと期待結果の再現性不足（P1）

- 対象: `TC-F011-BE-002`、`BE-003`、`BE-004`、`BE-007`、`BE-010`、`BE-013`、正常fixtureの名称契約
- 問題: 「同月」「1日目/2日目」「同日/別日」「任意文字列」「複数状態」「実HTTPの200/401/403」といった記述に、具体的な日付、report ID、案件/分類/休日キー、ログイベント、有限な入力集合がない。社員・名称も「既存master/snapshotと一致」とだけ記載される。
- 影響: テスト担当者が異なるfixtureを作っても同じケースを実行したことになり、期待値の差分や非対象データ混入を検出できない。再実行・Oracle cleanup・失敗再現の境界が曖昧になる。
- 判定: `不足`
- 標準化判定: **既存観点で対応**。テストケースレビューの「入力の具体性」「fixture再現性」「期待結果の観測可能性」で横展開する。
- 対応案: 各ケースに固定日付、固定ID、全名称、状態、数値、cleanupキー、ログのstatus/pathを記載し、`任意文字列`は有限な具体ベクトルへ展開する。

### FIND-F011-TC-REV-003: TC/RTと実テスト責務の不一致（P0相当）

- 対象: `月次集計_テストケース.md` §6/§8/§9、Backend/Frontendテストファイル
- 問題: 正本§9はControllerがBE-001～010/013～015を担うと表記するが、`MonthlySummaryControllerTest`の実メソッドは代表正常、BE-007、BE-008、BE-009/013、BE-014の7件である。BE-002～006B/010/012/013の実DB完全一致・副作用・ログ証跡は未実行。さらにFE-003は正本にあるが、専用の実テスト名がなくE2E-001へ暗黙吸収され、BEのRT名はハイフン表記とアンダースコア表記が一致しない。
- 影響: 「RTが存在する」「§9に書かれている」だけで受入条件を完了扱いでき、DB集計の誤GROUP BY、状態漏れ、境界漏れを見逃す。
- 判定: `不足`
- 標準化判定: **既存観点で対応**。AC→TC→RT→実メソッド/spec→コマンド→証跡の一意照合で検出できる。DB集計マトリクスの標準化は既存`FIND-F011-POST-BE-001`へ統合する。
- 対応案: §9を実在するメソッド単位へ修正し、FE-003へ専用RTを付けた実テストを追加するか、E2E-001への統合を正本で明記する。BE-002～006B/010/012/013はRepository/Oracle fixtureごとに実行結果を記録する。

### FIND-F011-TC-REV-004: 上位E2Eの完全一致不足（P1）

- 対象: `frontend/e2e/monthly-summary.spec.ts:7-62`、`frontend/e2e/monthly-summary.oracle.spec.ts:18-121`
- 問題: Mock E2EとOracle E2Eは、社員表の一部を個別cellで確認する一方、案件・分類・休日は主に`toContainText`またはキーの存在を確認している。各表の全行数、ID→名称→数値の集合一致、非対象キー不存在を一貫して確認していない。Unitの`FE-004`は行集合を完全一致するが、上位層の契約を代替しない。
- 影響: 案件P001/P002のように同値の行を入れ替える、余分なP999行を返す、Oracleの名称や非対象行を混入させるといった変異が、現在のE2Eアサーションでは通過する可能性がある。既知キーの一部の値は確認しているため、すべての誤値を見逃すという意味ではない。
- 判定: `不足`
- 標準化判定: **既存観点で対応**。期待結果の検出力と層別アサーションの既存観点で対応する。
- 対応案: 表ごとに可視panelを限定し、行を`ID→名称→値`へ正規化して順序非依存の完全一致、行数、非対象値不存在をMock/Oracle双方で確認する。

### FIND-F011-TC-REV-005: 再集計・再試行の操作未実行（P1）

- 対象: `TC-F011-FE-005`、`TC-F011-FE-006`、`frontend/test/MonthlySummaryPage.test.tsx:147-176`、`frontend/e2e/monthly-summary.spec.ts:64-78`
- 問題: 正本は空状態で「切替と再集計を継続可能」、400後で「再試行可能」と宣言するが、Unit/Mock E2Eは空メッセージ、旧値消去、年月保持までで、2回目の集計操作が成功することを実行していない。
- 影響: ボタンがdisabledのまま、二回目のrequestが発生しない、またはエラー後に状態が復旧しない不具合を検出できない。
- 判定: `不足`
- 標準化判定: **既存観点で対応**。異常後復旧、再試行、状態遷移、通信順序の既存観点で検出できる。
- 対応案: 空→正常、400→正常のdeferred応答を用意し、ボタン再操作、request回数、表示値復旧、alert消去をアサートする。

### FIND-F011-TC-REV-006: Oracleケースのfixture独立性不足（P1）

- 対象: `TC-F011-ORACLE-001`、`frontend/e2e/monthly-summary.oracle.spec.ts`、`backend/src/test/resources/db/oracle/e2e-verify.sql`
- 問題: Oracle verifyは`2099-12-01`のPENDING日報と`2099-12-02`のAPPROVED日報を検証するが、月次ケース自身が作るのは`2099-12-02`である。前者は別の日報Oracle specの実行順と共有DB状態に依存し、ケース・runnerの文書に依存関係が明記されていない。
- 影響: 月次spec単独実行、spec順序変更、前段cleanup変更でverifyが失敗または別データを誤検証する。ORACLE-001の「承認→集計」を一つの独立fixtureとして再現できない。
- 判定: `不足`
- 標準化判定: **既存観点で対応**。Oracleケースの独立性、固定fixture、cleanup、runner順序の既存観点で検出できる。
- 対応案: `2099-12-01`のPENDING生成を月次specへ移す、verifyを月次spec固有の行だけにする、または依存specと実行順を正本へ明記し単独実行を対象外にする。

## 6. 完了条件・次回確認

本レビューのケース判定を`OK`へ更新する条件は次のとおり。

1. 5休日区分、4承認状態、null/明細有無を固定fixtureで列挙し、各期待値を完全一致で観測する。
2. BE-002～006B/010/012/013を実DBまたは保護Oracle runnerで実行し、非承認除外、複数行集計、境界、read-only、認可順序、ログ非開示の成果物を回収する。
3. Mock/Oracle E2Eで4表の全行集合、名称、数値、非対象行不存在を確認し、FE-005/006の再集計・再試行を実操作する。
4. ORACLE-001のfixtureを独立化するか、依存specとrunner順序を正本へ明記し、verify/cleanupと整合させる。
5. FE-003の実テストを追加するか、ケースの責務を既存の別ケースへ統合してAC→TC→RT→実テストの孤立をなくす。
6. `9999-12`のOracle実機結果と、4本の照会の基準時点契約を決定する。
