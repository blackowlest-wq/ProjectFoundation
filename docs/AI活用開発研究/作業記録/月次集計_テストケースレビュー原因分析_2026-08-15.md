# 月次集計 テストケースレビュー指摘の原因分析

## 1. 結論

今回の指摘は、単純に「レビューを全部省略した」結果ではない。次の3種類が混在していた。

1. **手順上は検出済みだが、未達・保留のまま残っていたもの**
2. **手順は一部実施したが、レビュー範囲または検出力が足りず、後から見つかったもの**
3. **実装前の資料レビューと実装後の実テストレビューの境界がずれ、完了条件の証跡が弱くなったもの**

主因は、品質重視モードの手順そのものが存在しなかったことではなく、**実装後に全TCを「正本ケース→実メソッド/spec→コマンド→実行結果」へ一件ずつ突合するゲートを、完了判定の必須証拠として適用し切れなかったこと**である。

今回のケースレビューで新たに見つかった不足は、`FIND-F011-TC-REV-001`～`006`として記録した。既存のP0/P1保留を含む原因の総括は以下のとおり。

## 3. なぜ手順が漏れを止められなかったか

### 3.1 実装前レビューと実装後レビューの役割を混同した

実装前の`月次集計_テストケースレビュー.md`は、主に「資料上の欠落・矛盾・孤立を解消したか」を確認し、`P0/P1/P2の資料上の欠落・矛盾・孤立は解消した`と判定している。同じ文書は、実装後に実テスト名と実行結果を追記して再判定すると定めていた。

しかし実装後レビューでは、代表的なUnit/Controller、SQL形状、Frontend、Mock E2Eの成功と、未実行のP0を記録するところまでで、正本の全TCを実在するテストへ再突合する専用表を作らなかった。そのため、**資料の完成**と**実行可能なテスト契約の完成**が同じ「反映済み」と扱われた。

### 3.2 観点の選択はあったが、適用単位が粗かった

事前レビューの記録にある独立観点は、Frontend不足/配置、期待結果、トレーサビリティ、E2E/Oracle実行可能性である。これは必要な観点の一部を含むが、DBマスタの列挙値×状態×null/明細、複数行GROUP BY、再試行の状態遷移、E2Eの変異検出力を一つのマトリクスとして実施した記録にはなっていない。

つまり「テスト不足を確認する」という観点名はあったが、**どのTCのどの入力軸を、どの層で、どの完全一致アサーションで確認するか**まで分解されていなかった。

### 3.3 トレーサビリティが範囲記法中心になった

正本は`BE-001～BE-010`のような範囲で責務を表記し、実装後レビューも複数RTをまとめて記録した。これは一覧性は高いが、次の不一致を隠しやすい。

- 正本にあるBEケースと、実際のController/Service/Repositoryテスト数の差
- `RT-F011-FE-003`の専用テストがなく、E2E-001へ暗黙に吸収されたこと
- 正本のハイフンIDとJavaメソッドのアンダースコア名の検索不一致
- Oracle verifyが別specで作られるデータに依存すること

ケース単位の一意行を最終ゲートの必須入力にしなかったことが、今回の中心的なプロセス原因である。

### 3.4 「完全一致」の定義をテスト層ごとに分けなかった

正常値の指摘修正ではUnitの行集合を完全一致へ強化した。一方、Mock/Oracle E2Eは既知のIDと値を部分確認する形で残った。`完全一致`を「Unitで確認できれば上位層でも十分」と解釈したため、上位層でしか見えない余分な行、fixture接続、画面状態、runner前提を検出できなかった。

これは手順を完全に省略したというより、**期待結果レビューの検出力を層ごとに定義しなかった**ことによる検出失敗である。

### 3.5 レビュー中の固定点が弱かった

初回実装後レビュー中にOracle login helperやARIAテストが別修正で更新され、レビュー指摘が一時的に古い状態を指す事象があった。最終的には修正済みだが、レビュー開始時のcommit固定、レビュー中の変更凍結、再レビュー対象差分の明示が弱かった。

これは今回のDBケース不足の直接原因ではないが、指摘の鮮度を下げ、修正済みと未達の境界を不明瞭にするプロセス上の二次要因である。

## 4. superpowersをやめたこととの因果関係

今回の証拠から、**superpowersをやめたこと自体が直接原因だとは判定しない**。ProjectFoundationのpreflight/review Skillには、ケースレビュー、テスト構成、トレーサビリティ、未実行を成功扱いしないHard Gateが既に記載されていた。

問題は、任意のツール名ではなく、次の運用が実際のゲートへ落ちていなかったことである。

- 全TCを一件ずつ照合する担当・成果物がなかった
- 仕様・資料レビューと実装後の実行証跡レビューを同じ「反映済み」で閉じた
- 部分アサーションを完全一致とみなした
- 共有作業ツリーの変更を固定点として管理しなかった

したがって、superpowersを戻すことだけでは再発防止にならない。現在のProjectFoundation手順に、上記の証跡契約を強制的に組み込むことが必要である。

## 5. 再発防止の優先順位

1. **最優先**: 最終レビューに「TC一件一行」の照合表を必須化する。列は`AC/TC/RT/実メソッドまたはspec/コマンド/結果/証跡/保留理由`とし、未対応行が1つでもあれば完了不可とする。
2. **最優先**: DB集計は`列挙値×承認状態×null/明細×境界×複数行`のfixtureマトリクスを作り、DB概念設計・seed・Repository/Oracle結果を同じ行で照合する。
3. **高**: E2Eの期待結果に、可視panel限定、全行数、ID→名称→値の順序非依存完全一致、非対象行不存在、状態復旧を必須化する。可能なら同値入替え・余分行の変異で検出力を確認する。
4. **高**: Oracleケースは単独実行可能性、spec順序、共有DB前提、cleanup対象を正本に明記する。verifyが別specのデータを読む場合は、依存関係を受入条件として明示する。
5. **高**: レビュー開始時のcommit SHAを固定し、レビュー中の変更は別差分として再レビューする。共有worktreeの同時修正をレビュー完了の根拠にしない。
6. **中**: 「資料反映済み」「実テスト実行済み」「受入完了」を別ステータスにする。`要修正→反映済み`は文書更新だけでは付与しない。

## 6. 判定・記録

- 原因分析の主分類: **手順の不在ではなく、実装後の適用単位・証跡・検出力が不足した部分適用**。
- 既に見つかっていたもの: DB/Oracle/ログ/`9999-12`/snapshotのP0～P2保留。
- 後から見つかったもの: 列挙型、fixture再現性、TC/RT実体対応、E2E完全一致、再試行、Oracle独立性。
- 標準化判定: 上記の再発防止策は**標準化候補**として記録する。今回の報告では既存Skill本文・レビュー観点本文は変更せず、次回の標準化判断で反映先を決める。
