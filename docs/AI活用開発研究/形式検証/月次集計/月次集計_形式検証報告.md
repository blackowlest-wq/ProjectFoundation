# F-011 月次集計 形式検証報告

作成日: 2026-08-13
対象コミット: `4a61511`（`feat: add monthly summary`）
判定: **コードの主要な集計・認可関係は有限モデルで整合。2つの残余リスクを反例で確認したため、形式検証ゲートは「条件付き」**。

## 1. 目的と境界

今回の検証では、文書が宣言する受入仕様と、Backendコードから読める振る舞いを同じ有限データで表し、次を区別した。

1. 文書仕様そのものに対する反例
2. 文書仕様と実装の精密化関係に対する反例
3. 文書に明記されていないが、月次集計として自然な品質仮定に対する反例

有限モデルで反例がないことは、任意のDB件数・全ての日時・全ての同時実行を証明するものではない。SQLの実行結果とOracleの型境界は、既存のOracleゲートと併用して判定する。

## 2. ドメイン仕様の形式化

正本は A-016、S-008、V-OUT-003、`月次集計_テストケース.md` とした。対象年月 `M` に含まれる日報集合を次で表す。

```text
InMonth(M) = { r | Mの初日 <= r.reportDate < 翌月初日 }
Approved(M) = { r in InMonth(M) | r.approvalStatus = APPROVED }
```

宣言仕様の4集計は次の意味で固定した。

| 集計 | 形式化した定義 |
| --- | --- |
| 社員別作業時間 | `sum(coalesce(r.actualWorkMinutes, 0))` を社員単位に集計 |
| 案件別作業時間 | 承認済み日報明細の `workItemMinutes` を案件単位に集計 |
| 作業分類別作業時間 | 承認済み日報明細の `workItemMinutes` を作業分類単位に集計 |
| 休日区分別日数 | 承認済み日報の件数を休日区分単位に集計（同日・別社員は2件） |

承認済み行が0件の場合は、`yearMonth`を残し、4配列を空にする。ADMIN以外は集計を実行できない。

Z3、TLA+、Alloyの宣言モデルは、承認済み2行（E001/P001/WC001=480/420、E002/P002/WC002=360/360）と非承認1行を使い、4つの期待配列を完全一致させる。実行結果は全てPASSだった。

## 3. コード仕様の形式化

`MonthlySummaryService` と `JdbcMonthlySummaryRepository` から、次をモデル化した。

- ADMIN判定を年月解析より先に行い、拒否時はRepositoryを呼ばない。
- `^[0-9]{4}-[0-9]{2}$` と `YearMonth.parse` で年月を受け、`[from, to)` の半開区間を4本のSQLへ渡す。
- 4本のSQL全てに `approval_status = 'APPROVED'` を付ける。
- 社員集計は`COALESCE(SUM(work_minutes), 0)`、案件・分類・休日は明細／日報の承認済み集合を参照する。
- `@Transactional(readOnly = true)` の1トランザクション内で、社員→案件→分類→休日の順に個別照会する。

最初の4項目については、Z3で「宣言式とコード式が異なる」という有限反例を探索し、反例なし（UNSAT）を確認した。後半の2項目には下記の反例がある。

| 検査器 | 実行結果 |

### 4.2 反例 FM-F011-001: `9999-12`の翌月境界

```text
year = 9999
month = 12
next_year = 10000
```

Javaの厳密形式チェックは`9999-12`を受け付け、サービスは`plusMonths().atDay(1)`で`10000-01-01`を作る。Oracle DATEの上限を9999年と置くと、入力形式上は合法な対象年月がDB検索境界では表現できない。TLCは初期状態（`year=9999`, `month=12`）で`OracleDateSafe`違反を報告し、Alloyも`Request.nextMonthYear = Y10000`のインスタンスを生成した。

これは既存指摘 `FIND-F011-POST-DB-001` を形式モデルで再現したもの。仕様に存在しない年範囲制限を勝手に追加せず、Oracleでの応答／エラー契約を確定するまで保留する。

### 4.3 反例 FM-F011-002: 4集計の混在スナップショット

```text
employee_query_version = 0  -> 480分
project_query_version  = 1  -> 540分
```

TLA+の最短トレースは次の通り。

1. DB版0で社員集計を読む。
2. 承認処理がコミットし、DB版1になる。
3. 案件・分類・休日集計をDB版1で読む。
4. 4配列が同じ承認済み日報集合を表す保証がない。

Alloyでも`employeeQueryVersion=V0`、他3照会が`V1`となるインスタンスを生成した。これはA-016に明記された必須条件への直接違反とは断定しない。A-016が暗黙に「1回の月次集計は同一コミット済み集合を表す」と要求するならP1相当の不備であり、要求しないなら仕様の明文化不足である。対策候補は、単一SQL／共通CTE、明示的なスナップショット分離、または集計時点の世代番号を4結果に付与することである。

## 5. ドメイン用語へ戻した説明

### 5.1 9999年12月

「対象年月」は利用者が画面で選ぶ検索の境界であり、「DBが扱える日付範囲」と同じではない。現在の実装では、対象年月の最後の月を選べるかどうかと、承認済み日報を検索するための「翌月初」をDBが表現できるかどうかが分離している。

業務用語で言えば、**対象年月の選択可能範囲と、承認済み日報の検索期間の表現可能範囲が一致していない**。通常の業務年範囲を決めるか、上限時の「データなし／入力エラー」を受入条件に追加する必要がある。

### 5.2 4集計の混在

「月次集計」は、社員別作業時間、案件別作業時間、作業分類別作業時間、休日区分別日数が、同じ**承認済み日報の集合**を別の切り口で見たものと理解される。現在は4回のDB照会の途中で承認状態が変わると、社員集計だけが承認前、案件集計以降が承認後という組合せを返し得る。

業務用語で言えば、**1回の月次集計に含まれる承認済み日報の基準時点が、集計軸ごとにずれる可能性がある**。画面上は4タブが同じ対象年月を表示していても、利用者が比較する数字の母集団が一致しない。

## 6. 用語台帳の効果

既存の`日報登録画面_ドメイン用語台帳.md`はF-002を対象とし、月次集計を明示的に対象外としている。そのため今回の形式化では、次のような**間接的な効果**はあった。

- `社員`（認証上の`利用者`とは別）を社員別集計のキーとして扱えた。
- `APPROVED`を「承認済み」と読み替え、状態値の意味を日報の状態遷移と接続できた。
- `workMinutes`が日報の実勤務時間と日報明細の作業時間で文脈を変える問題を再確認できた。

一方、月次固有の「対象年月」「承認済み日報の集合」「休日区分別日数（社員日数）」「4集計の同一基準時点」は台帳に登録されておらず、月次文書から形式化へ移す際の明示的な参照記録もなかった。したがって、**役立ったが、今回の機能開発で正式に適用されたとは言えない**。F-011を台帳へ追加し、`workMinutes`の所有オブジェクト、休日の日数意味、集計基準時点を登録することを標準化候補とする。

## 7. 品質ゲートと生産性への含意

- superpowersを必須入口から外しても、preflight、実装後レビュー、トレーサビリティ、Frontend/Backend静的解析・Unit・Mock E2Eの既存ゲートは適用できた。
- 今回の形式検証は、通常のテストが通る代表データでは見つけにくい`9999-12`と照会間競合を検出した。品質面では、手順置換によるゲート欠落は確認されない一方、形式検証を追加しなければ残った可能性がある。
- 開発速度の向上について、superpowers使用時との同一尺度の所要時間・手戻り・欠陥検出率が記録されていないため、因果効果は判定不能である。今回観測できるのは、ローカル品質ゲートを維持したまま作業を進められたことと、Oracle E2E／Coverageが未実行のまま残っていることだけである。
- 形式検証はOracle E2E、実DBの複数行fixture、Backendログ捕捉の代替ではない。既存の`FIND-F011-POST-BE-001`、`FIND-F011-POST-GATE-001`、`FIND-F011-POST-SEC-001`は引き続き未達／保留である。

## 8. 結論と次の判定条件

1. 宣言された4集計と認可短絡は、今回の有限モデルでコードと整合した。
2. `9999-12`境界は再現可能なP2残余リスクとして保留する。
3. 4集計の同一基準時点は、仕様に明記されていないため、P1相当の導出品質仮定として利用者・設計で決める。
4. F-011の完了判定は、既存のOracle E2E／CoverageゲートとDB fixture・ログ証跡が揃うまで条件付きのままとする。
