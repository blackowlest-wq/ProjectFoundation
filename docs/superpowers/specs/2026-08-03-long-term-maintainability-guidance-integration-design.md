# 長期保守可能性方針の既存資料反映 設計

## 目的

`長期保守可能性を重視した品質方針.md`を、コード、レビュー、設計判断、作業記録へ反映する。ただし、確認項目を単純に追加するのではなく、既存観点を目的・検出方法・証拠・重複・負荷で棚卸しし、統合、優先度変更、自動化、削除候補を整理する。

## 背景

SIer向けシステムでは、長期保守、担当者交代、業務知識の不足、古いシステムの調査改修、障害時の影響判断、仕様と実装の不一致が発生する。将来の保守担当者が根拠を追跡しながら理解、変更、検証、障害調査・復旧できることを品質の中心に置く。

一方、品質特性は加算できず、確認項目を増やすと、記録負荷、レビュー時間、開発速度、確認の深さへ影響する。そのため、長期保守可能性を既存の観点へ追加するだけでなく、何を維持し、何をリスク適用へ移し、何を自動化・統合・削除候補とするかを整理する。

## 設計上の決定

### 1. 既存資料への反映を基本とする

長期保守可能性専用のレビュー・品質ゲートを新設しない。既存資料の役割を保ったまま、長期保守可能性を観点の選択と成果物の追跡に使う。

### 2. 品質観点を3層に分ける

- **絶対条件**: 正しさ、安全性、セキュリティ、法令・契約要件。変更内容を理由に下げない。
- **全変更の必須核**: 変更影響を把握できること、変更結果を検証できること、重要な判断・前提を追跡できること。
- **リスク適用観点**: 構造理解、ログ・障害調査、復旧、性能、互換性、アクセシビリティ、移行など。変更リスクに応じて適用する。

自動化できる検査は、可能な限り人間の確認から自動検査へ委譲する。自動検査と人間レビューが同じ内容を繰り返している場合は、重複を棚卸しする。

### 3. ADRを重要な設計判断の正本とする

現行プロジェクトにはADRの仕組みがないため、重要な設計判断を残すための最小限のADRを導入する。作業記録や統合品質記録へ設計理由を重複転記しない。

ADRの対象は次に限定する。

- 複数機能へ影響する構造や共通部品
- API、DB、外部システムとの契約
- 認証認可、セキュリティ、ログ、復旧に関わる制約
- 将来の変更方法を強く制約する方式
- 複数の代替案から選択した重要な判断

局所的で影響範囲が小さい判断は、必要に応じてコードコメントまたは作業記録へ残し、ADRを必須にしない。

ADRの保存先は `docs/AI活用開発研究/設計判断記録/` とし、最小様式を `ADRテンプレート.md` に定義する。個別ADRは1判断1ファイルとし、状態、背景、決定、代替案と不採用理由、前提・制約、影響・リスク、安全性を確認したテスト・レビュー、影響範囲、関連資料を記載する。判断を変更する場合は既存ADRを直接書き換えず、新しいADRで置き換え関係を示す。

AIを利用した場合も、対話全文や生成コードの行単位の採用範囲は保存しない。判断に影響した場合だけ、AIを調査補助、案の比較、実装案の下書きなどに利用したことと、人間が最終決定した内容をADRまたは作業記録へ残す。コード差分、レビュー結果、テスト結果を、生成範囲を記録する代わりの証拠とする。

## 既存資料ごとの責務

| 資料 | 初回反映内容 |
| --- | --- |
| `長期保守可能性を重視した品質方針.md` | ADRの役割、記録の分担、既存資料を無条件に増やさない方針を追記する |
| `開発フロー.md` | 3層の適用、ADR要否の判断、観点の棚卸しを標準フローへ組み込む |
| `実装前チェック表.md` | ADRの既存参照・新規作成・対象外理由、変更影響、検証方法、重要判断の確認を既存項目へ組み込む |
| `実装後レビュー表.md` | ADR整合性、後任者が判断・影響・検証根拠を追跡できることを既存レビューへ組み込む |
| `設計判断記録/ADRテンプレート.md` | 重要な設計判断の最小記録形式を定義する |
| `標準化/標準化資料一覧.md` | ADRの保存先と用途を案内する |

次の資料は、今回の初回反映では改訂しない。

- `テストケースレビュー観点.md`
- `テスト方針.md`
- `テスト・静的解析チェック表.md`
- `品質ゲート運用.md`
- `統合品質記録様式.md`

テスト関連資料の主題は、仕様・業務ルールに対する動きの正しさ、期待結果、異常系、境界値、権限、状態遷移、テスト責務分割である。長期保守可能性との接点は、テストが変更後の安全性を示す実行可能な証拠になることに限定する。

品質ゲート運用は、どのMode、CI job、runnerで、どの範囲をいつ判定するかを定める正本である。新しいjobや段階を追加せず、既存のpre-commit、pre-push、影響範囲CI、夜間・リリース前の全体CIを維持する。品質ゲートの成功は自動検査の成功を示すものであり、ADRや設計判断の妥当性まで自動保証するものではない。

## コードへの反映

保守性を理由に、コメントや設計書を一律に増やさない。次の役割分担を維持する。

- 構造、型、命名: 実装そのものによるHow
- コードコメント: コードだけでは誤読しやすい処理順、分岐、制約、局所的な`Why not:`
- ADR・設計・作業記録: 全体構造の理由、代替案、前提、リスク、人間の最終判断
- テスト: 保証する動きと期待結果
- 設定・CI・ログ: 実際に実行される条件と観測結果

レビューでは、責務・境界・公開契約・副作用・変更影響がコードから追跡できるかを確認する。コメント数やドキュメント量を品質指標にしない。

## レビューへの反映

ADR専用の独立レビューは設けない。既存の設計照合、トレーサビリティ、AI生成物レビューへ統合する。

レビューでは、次を確認する。

1. 今回の変更にADRが必要か。必要なら既存ADRを参照したか、新規ADRを作成したか
2. 実装がADRの決定、前提、制約と一致しているか
3. ADRで却下した方式を意図せず再導入していないか
4. ADRのリスクや影響を、テスト、ログ、運用確認で確認できているか
5. ADRが不要な局所判断の場合、コード構造、コメント、テストで判断根拠を確認できるか

AI生成物レビューは、AIが生成したコードの範囲を棚卸しするのではなく、最終成果物が仕様、ADR、テスト、セキュリティ要件と一致するかを確認する。レビュー結果は、ADR、テスト、コード差分、統合品質記録へのリンクで追跡する。

## 既存観点の棚卸し方法

既存のチェック項目は、次の項目で評価する。

| 評価項目 | 確認内容 |
| --- | --- |
| 守る品質 | 正しさ、セキュリティ、契約、変更影響、障害調査など何を守るか |
| 防ぐリスク | 省略した場合に何が起きるか |
| 検出方法 | 人間レビュー、テスト、静的解析、CI、運用確認のどれで検出するか |
| 証拠 | 判定結果がコード、テスト結果、レビュー記録、ADRなどのどこに残るか |
| 重複 | 他の観点や自動検査と同じ欠陥を見ていないか |
| 負荷 | 実施、記録、維持にどの程度の負荷があるか |
| 適用範囲 | 全変更、特定リスクの変更、夜間・リリース前だけのどれか |

評価後の分類は、絶対条件、全変更の必須核、リスク適用、自動検査への委譲、統合、廃止候補とする。負荷だけを理由に削除せず、過去の障害、レビュー指摘、検出実績、契約・セキュリティ上の必要性、他の検査との重複を確認する。

## 段階導入

### 第1段階: 記録の役割を定義する

ADRの最小様式と適用条件を定義し、作業記録、統合品質記録、コードコメント、テストとの役割分担を既存資料へ反映する。AI対話の全文保存や生成コードの範囲記録を必須にしない。

### 第2段階: 既存3資料を改訂する

`開発フロー.md`、`実装前チェック表.md`、`実装後レビュー表.md`へ、3層の適用、ADR要否、設計判断の追跡、後任者の確認視点を組み込む。テスト方針、ケースレビュー観点、品質ゲート運用は変更しない。

### 第3段階: 複数機能で試行する

CRUD、業務フロー、DB・外部連携など性質の異なる機能で試行し、ADR境界、後任者による追跡可能性、レビュー・記録負荷、重複記録、既存ゲートへの影響、欠陥検出への影響を確認する。

### 第4段階: 規約を整理する

試行結果に基づき、重複観点を統合し、効果の低い観点の優先度を下げ、根拠がない項目を削除候補とする。効果が確認できないまま、新しい必須項目を追加し続けない。

## 非対象

- テスト方針やケースレビュー観点を、保守性中心へ作り替えること
- 品質ゲートのjob、runner、実行段階を新設・変更すること
- AI対話全文や生成コードの行単位の採用範囲を保存すること
- すべての変更にADRを要求すること
- コメント数、ドキュメント量、AI指摘件数を品質指標にすること

## 完了条件

- 重要な設計判断をADRで追跡できる
- 作業記録、統合品質記録、コードコメント、テスト、ADRの役割が重複していない
- 全変更の必須核と、リスク適用観点が区別されている
- 既存のテスト方針、ケースレビュー観点、品質ゲート運用を不必要に変更していない
- 後任者が設計理由、変更影響、検証根拠、障害調査情報を追跡できる
- 既存観点の削減・統合・優先度変更が、リスク、検出実績、重複、負荷の根拠で説明できる
- Markdownlint、UTF-8、リンク、差分チェックが成功する
