# 長期保守可能性を重視した品質方針の設計

## 目的

SIer向けシステムの長期保守を前提に、コードだけでなく、設計、テスト、運用、ドキュメント、AI利用時の判断記録まで含めて品質を捉える上位方針を、構想メモへ追加する。

この文書は、構想メモ本体を作成するための設計記録である。詳細なチェック項目、記録様式、障害対応手順を新たに定義するものではない。

## 背景

本プロジェクトは、数年単位でシステムを保守するSIer向けの開発環境を検討している。開発者と保守担当者が異なること、協力会社や担当者が入れ替わること、保守担当者が業務知識を十分に持たない場合があること、古いシステムを調査して改修すること、障害時に短時間で影響範囲を判断する必要があること、仕様書と実装が一致しない場合があることを前提とする。

AIとの対話では、設計理由、却下した代替案、リスク、仕様上の前提、安全性を確認したテスト、人間が行った判断が最終成果物へ残りにくい。そのため、将来の担当者が根拠を追跡しながら安全に理解、変更、検証、障害調査・復旧できることを、品質方針の中心に置く。

## 対象読者

第一の読者は、将来の保守担当者、協力会社、引継ぎ担当者とする。現在の開発者、AI利用者、レビュー担当者は、保守担当者が必要な情報を追跡できる状態を作るための副次的な読者とする。

## 追加する構想メモの位置づけ

追加ファイルの仮タイトルは `長期保守可能性を重視した品質方針.md` とする。配置先は `docs/AI活用開発研究/構想メモ/` とする。

既存資料との関係は次のとおりとする。

| 資料 | 役割 |
| --- | --- |
| `品質向上施策メモ.md` | AI活用による品質向上の研究方針 |
| `長期保守可能性を重視した品質方針.md` | 長期保守を前提に、何を品質とみなすかを示す上位方針 |
| `標準化/開発フロー.md` | 方針をIntakeからRecordまでの開発手順へ落とし込む |
| `標準化/実装前チェック表.md`、`実装後レビュー表.md` | 方針を実装前後の確認へ落とし込む |
| `標準化/テスト方針.md`、`テストケースレビュー観点.md` | 方針をテスト範囲、テスト層、責務分割、レビューへ落とし込む |
| `標準化/統合品質記録様式.md`、`作業記録テンプレート.md` | 方針に基づく判断、結果、指摘の記録を集約する |

新しい構想メモは、既存資料のチェック項目や記入欄を再掲しない。既存資料が必要な理由を説明し、詳細資料への導線を示す。

## 文書で定義する中心概念

長期保守可能性は、次のように定義する。

> 長期保守可能性とは、システムを十分に知らない担当者であっても、必要な情報を追跡しながら、安全に理解し、変更し、検証し、障害時に調査・復旧できる性質である。

保守容易性をコード品質の同義語として扱わず、構造理解、影響把握、変更結果の検証、障害調査・復旧、担当者交代後の知識継承を含む上位概念として扱う。

## 品質の優先順位

以下は絶対条件とする。

- 正しく安全に動作すること
- セキュリティ要件を満たすこと
- 法令・契約要件を満たすこと

絶対条件を満たした上で、長期保守に関する優先順位を次のとおり示す。

1. 変更影響を把握できること
2. 変更結果を検証できること
3. 未経験者でも構造を理解できること
4. 障害時に原因を調査し、必要な復旧につなげられること
5. 実装やリリースが速いこと

これは速度を否定する方針ではなく、速度だけを理由に、影響範囲、検証方法、構造、障害調査に必要な情報を失わせないという基本姿勢を示す。速度優先時の例外申請、期限管理、再確認条件はこの文書の対象外とする。

## 長期保守可能性を支える品質領域

詳細なチェック項目は標準化資料へ委ね、各成果物が保守にどのように貢献するかを示す。

| 品質領域 | 保守担当者が確認できるべきこと |
| --- | --- |
| 設計 | システムの構造、責務、境界、前提、重要な設計判断 |
| 実装 | 処理の責務、契約、制約、変更してよい範囲、影響を受ける範囲 |
| テスト | 何を保証しているか、変更時に何を再確認すべきか、異常系や境界値の扱い |
| 運用 | ログや相関IDから何が起きたかを調査できること、復旧判断に必要な情報があること |
| ドキュメント | 全体像、処理・データフロー、外部境界、実行方法、重要ルール、設計理由 |
| AI利用 | AIの提案と人間の最終判断を区別できること、採用・修正・不採用の理由を追跡できること |

## ドキュメントの量ではなく、保守価値と更新可能性を重視する

ドキュメントは多いほど保守性が高まるわけではない。更新されない資料や、コードをそのまま日本語化しただけの説明は、実装との不一致を増やし、誤った判断を生む可能性がある。

残す価値が高い情報は、次の3群を中心とする。

- 全体像・境界: システム全体の構成、処理・データフロー、外部システムとの境界
- 実行・調査: ローカル実行方法、テスト実行方法、障害調査方法
- 判断・制約: 重要な設計判断、変更してはいけない制約、業務上の重要ルール

コード、テスト、設定、CIなどの実行可能な情報を一次的な根拠とし、文書はそれらから読み取りにくい理由、全体像、境界、制約、運用上の判断を補う。文書を追加するときは、誰のどの判断に役立つか、何が変わったときに更新するか、実装や実行可能な情報との不一致をどう防ぐかを考える。

## AI利用時は、対話履歴ではなく判断結果を残す

AIとの会話をすべて保存することを目的にしない。対話には途中案や誤った提案も含まれ、そのままでは後任者にとって信頼できる設計資料にならないためである。

AIとの対話から人間が確認し、採用した最終的な判断として、少なくとも次の情報を追跡できるようにする。

- 何を実現する変更だったか
- どの設計・実装案を採用したか
- なぜその方式を採用したか
- どの代替案を検討し、なぜ採用しなかったか
- どの仕様、制約、業務ルールを前提にしたか
- どのリスクを認識しているか
- AIが生成した内容のうち、どこを人間が確認、修正、採用したか
- どのテストやレビューで安全性を確認したか

AIの出力は提案または下書きとして扱い、採用の根拠と最終判断は、人間が後から追跡できる形で残す。AIとの対話そのものを正本とはしない。具体的な記録先と記録様式は、既存のAI利用ログ、作業記録、統合品質記録へつなぐ。

## 保守担当者から見た確認視点

方針を実務へ結びつけるため、保守担当者が次の問いに答えられる状態を目指す。

1. この機能・処理は何を実現し、何を保証するものか
2. どのファイル、データ、外部システム、業務ルールに関係するか
3. なぜ現在の構造・方式になっているか
4. 変更後の安全性を、どのテスト、レビュー、確認で判断できるか
5. 障害時に、どこから調査し、どの状態を確認し、どう復旧につなげるか

これらに答えられない場合は、コードだけでなく、設計、テスト、ログ、運用情報、ドキュメントのどこかに保守上の不足がある可能性がある。

## 完了条件

構想メモ本体は、次の条件を満たすものとする。

- SIerの長期保守特性と、今回の品質方針の背景が説明されている
- 長期保守可能性が、理解、変更、検証、障害調査・復旧、知識継承を含む概念として定義されている
- 絶対条件と、長期保守に関する品質の優先順位が分離されている
- ドキュメントを増やしすぎない方針と、残す価値が高い情報が示されている
- AIの対話履歴ではなく、人間の判断結果を残す方針が示されている
- 既存の標準化資料との役割分担と参照先が示されている
- 詳細チェック表、記録様式、障害手順、例外承認の仕組みを重複して定義していない
- UTF-8で保存され、日本語の文字化けがない
