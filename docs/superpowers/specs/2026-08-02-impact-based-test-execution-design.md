# 影響範囲ベーステスト実行への移行 設計書

**作成日:** 2026-08-02

## 目的

小規模開発ではmain push後の全テスト・全カバレッジを許容しつつ、大規模化しても実行時間とCI費用を抑えられるよう、通常実行を変更影響範囲へ限定する。全体テストと全体カバレッジは夜間またはリリース前の品質ゲートとして維持する。

## 設計方針

### 1. 実行層

| 実行タイミング | 基本範囲 | 目的 |
| --- | --- | --- |
| 開発中 | 変更機能、直接・推移的な依存先、契約テスト | 速いフィードバック |
| Pull Request / 通常CI | 影響範囲、変更層の静的解析、主要スモーク | 変更単位の回帰検出 |
| main push後 | 影響範囲を基本とし、重大変更は全体へフォールバック | 通常反映の品質判定 |
| 夜間 | 全テスト、全カバレッジ、全E2E、必要なOracle | 影響分析から漏れた回帰の検出 |
| リリース前 | 全テスト、全カバレッジ、全E2E、必要なOracle | リリース判定 |

### 2. 影響範囲の判定

- 画面・APIの局所変更は、対象機能のUnit/API/E2Eと直接利用元を実行する。
- 共通部品、認証・認可、CSRF、例外処理、業務ルール、DB/SQL、マスタ、共有fixtureの変更は、利用元と関連契約テストを含める。
- workflow、テストrunner、テスト発見規約、集約ビルド、依存関係、カバレッジ設定の変更は、影響範囲を限定せず該当層の全体テストへ拡張する。
- 依存関係を判定できない、影響範囲が密結合で分離できない、または変更が高リスクの場合は全体実行へフォールバックする。
- 自動判定だけで成功扱いにせず、選択した範囲・除外範囲・フォールバック理由を実行記録へ残す。

### 3. カバレッジ

- 通常実行では、変更行・変更モジュール・影響範囲のカバレッジを確認し、変更部分の分岐未充足を優先して扱う。
- 全体カバレッジの指標は、夜間またはリリース前の全体実行で再生成し、全体の退行を確認する。
- 全体カバレッジの数値だけで、変更機能のテスト十分性を代替しない。
- 変更範囲の抽出ができない場合は、全体カバレッジへフォールバックする。

### 4. 構造上の制約への対応

密結合により影響範囲を分離できないことは、全体実行へフォールバックする正当な理由とする。ただし、長期的には次の改善候補として記録する。

- 共通部品の責務分割
- 依存方向とモジュール境界の明確化
- 機能単位のfixture・DBデータ分離
- API/イベントなどの契約テスト追加
- テスト影響分析に利用できる依存グラフの整備

## 成功条件

- 3資料が同じ実行層、影響範囲、全体実行、カバレッジ、フォールバックの定義を持つ。
- 通常実行を全体実行と誤認しない。
- 未実行・除外・影響範囲不明を成功扱いにしない。
- 夜間・リリース前の全体実行を省略しない。
- Skillの編集元と`.agents`の配置内容が一致する。
