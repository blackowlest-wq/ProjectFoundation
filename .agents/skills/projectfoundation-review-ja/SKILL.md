# ProjectFoundation Review

## 目的

実装後の確認を、汎用的な感想ではなく、受入条件・テストケース・実テスト・指摘・標準化判断まで追跡できる独立レビューとして完了する。

## 開発モードの選択

作業開始時に利用者へ`簡易修正モード`または`品質重視モード`を確認し、選択結果を1枚の変更記録へ残す。選択後、変更カテゴリや規模を理由に自動で別モードへ切り替えない。

品質重視モードでは、このSkillの観点別独立レビュー、統合レビュー、P0/P1/P2判定、正本ケース、実装後レビュー文書、影響範囲判定、最終品質ゲートを適用する。通常の最終品質ゲートは、変更機能と影響範囲を基準に判定し、夜間・リリース前の全体ゲートとは分けて記録する。簡易修正モードでは、個別変更向けの専用実装後レビュー文書を作成せず、コード差分の独立レビューを1回行い、受入条件3～5項目、Focused UnitまたはN/A理由、表示確認、対象層チェック、`main` push後のCI委譲、残るリスクを1枚の変更記録へ記録する。

SimpleでもAPI契約、DB、DDL、SQL、業務ルール、状態遷移、入力検証、CI、workflow、品質ゲートを対象外にしない。既存pre-commit / pre-push hookと`main` push後の6品質jobは維持し、全テスト、coverage、全E2E、Oracle、追加secret scanをローカル未実行のまま成功扱いにしない。
表示要件のBrowserCaseが起動できない、または未実行の場合は、表示要件の品質ゲートを合格と報告しない。`BrowserManualReason`は未実行理由の記録であり、実ブラウザ確認の証拠ではない。`BROWSER_UNVERIFIED`や非0終了を確認した場合は、実行済みのUnit/lint/typecheck/buildと分離して記録する。

## Hard Gate

品質重視モードでは、観点別独立レビューと統合レビューが終わる前に、通常の影響範囲ゲートも夜間・リリース前の全体ゲートも完了扱いにしない。テストを追加・変更する場合は、影響範囲選定と全体実行の前にテスト構成・責務分割の判定と記録を終える。影響範囲の根拠、除外範囲、フォールバック条件を説明できない場合は、局所成功で完了扱いにせず全体実行へ切り替える。Fullが成功していても、テストファイルの責務境界・テスト層・配置・共有supportの確認が未完了ならレビュー完了扱いにしない。簡易修正モードでは、コード差分の独立レビュー1回と簡易記録の必須項目を完了条件とし、CI必須チェックを別の最終判定として維持する。

レビュー前にFullを実行した場合は「ベースライン確認」と記録し、指摘修正後に通常の影響範囲ゲートまたはフォールバック後の全体ゲートとして、Full、E2E、coverage、Oracleなど対象範囲の最終確認を再実行する。未実行、条件付きskip、対象外理由未記録の確認項目は成功扱いにしない。

## 品質重視モードの影響範囲判定

- 変更ファイル、差分、関連設計書から、まず変更機能を機能名またはユースケース名で特定する。ファイル名の列挙だけで済ませない。
- 変更機能ごとに、直接依存、推移的依存、契約テスト、直接利用元、共通部品、共有fixture / support、認証認可 / CSRF / 入力検証、DB / SQL / DDL / マスタ、workflow / test runner / 集約build / 依存関係 / coverage設定への影響を判定する。
- 影響範囲の記録では、少なくとも `選択した範囲`、`除外した範囲`、`各範囲の根拠`、`通常ゲートで実行する確認項目`、`全体実行へフォールバックしたか`、`フォールバック理由` を残す。
- 影響範囲が不明、依存関係を追跡できない、密結合で分離できない、高リスク変更、またはworkflow / test基盤 / coverage設定変更により選択ロジック自体を信用できない場合は、通常判定を全体実行へフォールバックする。
- 共通部品、認証、DB、状態遷移、workflowに影響する変更では、影響先を限定できる根拠がなければ、代表テストだけで完了扱いにしない。
- 除外したテスト層、E2E、Oracle、coverage確認は、除外理由と再確認条件がない限り対象外にしない。

## 品質重視モードの通常ゲートと全体ゲート

- 通常ゲートでは、変更機能、直接・推移的依存、関連契約テスト、必要な表示確認、必要なOracle確認、対象層の静的解析を影響範囲ベースで完了する。
- 通常ゲートのcoverage確認は二層化し、変更行・変更モジュール・影響範囲のcoverageと分岐未充足を確認する。抽出できない場合、または共有設定変更で範囲の信頼性が崩れる場合は、全体coverageへフォールバックする。
- 夜間・リリース前の全体ゲートでは、全テスト、全体カバレッジ、全E2E、必要なOracleを実行し、通常ゲートとは別の結果として記録する。
- 通常ゲートの成功だけで、夜間・リリース前の全体ゲート完了を代替しない。逆に、全体テストや全体カバレッジの成功だけで、変更機能のFocused Unit、契約テスト、主要E2E、必要なOracle確認、テスト構成レビューを省略しない。
- Full、coverage、E2E、Oracle、BrowserCase、secret scanを未実行・skip・委譲した場合は、成功ではなく未達、CI委譲、または保留として記録する。

## 実装後の確認契約

- `実装後レビュー表.md`、`テスト・静的解析チェック表.md`、`テスト方針.md`、正本ケース、受入条件レビュー、実装前レビュー結果を入力とし、観点名だけの汎用レビューにしない。
- 品質重視モードのレビュー記録には、変更機能、直接依存 / 推移的依存、共通部品 / 認証 / DB / workflow影響、選択した範囲、除外した範囲、根拠、通常ゲート結果、夜間・リリース前の全体ゲート結果、フォールバック理由を残す。
- セキュリティ、原因分析、影響範囲など複数領域を確認する場合は、`superpowers:dispatching-parallel-agents` で独立に確認し、担当間で結論を共有せず最後に統合する。
- 外部レビューやサブエージェントの指摘は、`superpowers:receiving-code-review` を使って仕様・コード・テスト上の妥当性を確認してから対応する。鵜呑みにして修正しない。
- 主要機能完了後またはマージ前は、必要に応じて `superpowers:requesting-code-review` を使う。セキュリティ観点はCodex Securityの利用可否を判定する。
- 不具合や再現失敗は、`superpowers:systematic-debugging` により再現、原因候補、検証、修正、回帰テストの順で確認する。既存参照と影響範囲は検索で追跡する。
- 過去障害の全件照合は必須にせず、対象機能の回帰、同一原因、高リスク領域に関係する場合だけ参照する。

## 実装後レビューの確認内容

- 仕様、受入条件、対象外、入力検証、業務ルール、状態遷移、DB整合性、認証認可、CSRF、既存導線、ファイル配置、責務、共通化、テスト構成・責務分割、コメント、テスト、静的解析を確認する。
- 変更対象のテストを、テストファイル、責務、テスト層、対象本番モジュール、ケースID/実テストIDへ対応付ける。変更機能に対する直接依存・推移的依存、共通部品、共有support、認証、DB、workflow影響を洗い出し、選択したテスト範囲と除外した範囲を理由付きで記録する。認証、一覧、登録・編集など独立責務の混在、Unit/UI/E2E/Oracleの不必要な混在、共有supportへの切り出し漏れを確認し、分割または維持の理由を記録する。
- 本体コードはHow、テストコードはWhat、コミット本文はWhy、コメントは必要なHow/Why notを担うことを確認する。`if`/`else`の処理手順は`How:`で示し、`Why not:`だけにしない。
- 指摘がない場合も、確認した観点、通常ゲート/全体ゲートの実施状況、残るリスクを記録する。指摘がある場合は、仕様根拠、対応テスト、標準化判定、反映先または保留理由・再確認条件を記録する。

## 指摘対応契約

- 指摘ごとに妥当性、対応・保留・非対応、対応順、修正ファイル、確認テスト、標準化判定を整理する。
- 修正後は該当テストと必要な回帰テストを再実行し、最終品質ゲートを完了するまで完了扱いにしない。
- 標準化候補は、レビュー観点、チェック表、テストケース様式、受入条件、サンプル、テストデータのどこへ反映するかを具体化する。標準化しない場合は個別対応で十分な理由を残す。

## 手順

1. 差分、対象範囲、正本ケース資料、受入条件レビュー、実装前の保留事項を確認し、変更機能を機能名またはユースケース名で特定する。
2. ケースIDごとに、仕様根拠、期待結果、対象コード、実テストID/コマンドを照合する。変更機能に対する直接依存、推移的依存、共通部品、共有support、認証、DB、workflow影響を確認し、選択した範囲、除外した範囲、根拠、フォールバック有無を記録する。正本ケースが更新されていなければ、レビュー完了扱いにしない。あわせてテスト構成・責務対応表を確認し、実テストが責務境界とテスト層に沿って配置されているかを影響範囲選定前に判定する。
3. 上記の参照契約からレビュー範囲を選定し、各担当へ具体的な参照ファイルと節を明示して独立に実行する。P0は必須、P1/P2は適用条件に基づいて選定する。各担当には他担当の結論を渡さず、対応する専門プロンプトの出力形式を使う。「テスト不足」「セキュリティ」のような観点名だけを渡してはならない。
4. 2つ以上の独立レビューを依頼する場合は、**REQUIRED SUB-SKILL:** Use superpowers:dispatching-parallel-agents とし、最後に統合担当を置く。
5. 統合担当は重複、矛盾、重大度、仕様根拠、テスト要否、保留条件を整理し、1件ごとに判定する。
6. 指摘を修正し、修正したファイルと修正を確認するテストを記録する。保留は理由と再確認条件を必須とする。
7. テスト構成・責務分割の指摘を修正または保留判定した後に、通常ゲートでは対象テスト、回帰テスト、型チェック、lint、build、必要なE2E、変更行 / 変更モジュール / 影響範囲のcoverage、必要なOracleを計画どおり実行する。夜間・リリース前、または影響範囲不明・密結合・高リスク・workflow変更などでフォールバックした場合は、全テスト、全体カバレッジ、全E2E、必要なOracleを全体ゲートとして実行する。実行しない項目、skipした項目、CIへ委譲した項目は理由と再確認条件を記録し、成功扱いにしない。
8. 通常ゲートの結果と、必要に応じて夜間・リリース前またはフォールバック後の全体ゲート結果を記録した後に、作業記録、指摘一覧、レビュー記録、正本テストケース、受入条件レビューを揃える。

## 標準化判定

指摘を作業記録と指摘一覧へ転記するだけでは完了としない。各指摘について、今回限りか再発し得る一般観点かを判定する。

- 状態別操作、読込中/失敗時の安全側制御、UIと保存処理の判定共有は、画面機能の標準レビュー観点・テストケース様式へ反映する。
- null、境界値、異常系、APPROVEDなどのテスト不足は、テストケースレビュー観点と期待結果レビューへ反映する。
- 受入条件・ケース・実テストの紐付け不足は、トレーサビリティ様式へ反映する。
- 標準化しない場合は、個別事情である理由をレビュー記録へ残す。

受入条件ID、テストケースID、実テストID、指摘IDは別名前空間にし、同じ文字列を再利用しない。
